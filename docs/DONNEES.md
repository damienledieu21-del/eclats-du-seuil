# Données et validation (lots 3 à 6, correctifs 6.1 et 6.1.1, sous-lots 7.1 à 7.3, sous-lots 8.1 à 8.5, sous-lots 11.4a à 11.4d, sous-lots 11.5, 11.9 et 12.1, sous-lots V1.2, V1.3 et V1.4)

## Fichier de règles

`data/v0/rules.json` centralise tous les paramètres de `StatRules`, `DamageRules` `ProgressionRules` (bloc `progression`, lot 4) et `CombatRules` (bloc `combat` : `tickMs`, `globalCooldownMs`, `endurance.*`, `limits.*` au lot 5 ; `guard.*`, `parry.*`, `rampartCharges.*`, `resonance.*` au lot 6 ; `guard.breakStatus` au lot 7.2 ; `triggers.areaStrikeMinCooldownMs` au sous-lot 8.4 ; `movement.*` et `contact.*` au sous-lot 11.4a, voir ci-dessous) et le catalogue des altérations (bloc `statuses` à la racine de `data`, lot 7.2). Toutes les valeurs provisoires du moteur y sont, aucune n'est codée en dur. `schemaVersion` vaut 4 depuis le lot 7.2 (voir « Versions de format »). Le schéma `data/schemas/rules.schema.json` sert à l'auto-complétion dans les éditeurs ; la validation qui fait foi est celle du programme.

```json
{
  "$schema": "../schemas/rules.schema.json",
  "schemaVersion": 4,                    // forme du fichier ; changement incompatible = +1, sans migration en pré-alpha
  "kind": "rules",                       // type de fichier attendu
  "contentVersion": "0.4.1-provisoire",  // version SemVer des valeurs
  "data": { "stats": { … }, "damage": { … }, "progression": { … }, "combat": { … }, "statuses": [ … ] }
}
```

Tous les champs sont obligatoires (sauf les champs facultatifs d'une altération, ci-dessous) : aucune valeur par défaut silencieuse. Décimaux à 4 décimales au plus, sans exposant ; entiers sans décimale.

Identifiants stables utilisés comme clés : attributs `force`, `dexterite`, `intelligence`, `vitalite`, `volonte`, `endurance` ; types de dégâts `physique`, `magique` ; arrondis `halfAwayFromZero`, `halfToEven`, `towardZero`, `floor`, `ceiling`.

## Garde des boucliers (sous-lot V1.2)

Chaque bouclier porte sa garde (« des boucliers qui changent la garde », [PLAN_VALLONS_SOLO.md](PLAN_VALLONS_SOLO.md#v12--équipement-complet--places-boucliers-écran-l)) : la **part des dégâts bloquée** en garde, l'**endurance d'un blocage** et la **fenêtre de parade**. Elle remplace, pour son porteur seulement, les valeurs de base `combat.guard.damageReduction`, `combat.guard.costPerBlock` et `combat.parry.windowMs` ; les modificateurs des talents et des passifs s'y ajoutent comme avant ([FORMULES.md](FORMULES.md#garde-du-bouclier-sous-lot-v12)). Sans bouclier (scénarios d'entraînement, mannequin, réseau), rien ne change.

Les règles (schéma 13) en fixent les bornes de jeu, dans le bloc `combat.shield` (valeurs provisoires) :

```json
"shield": {
  "minDamageReduction": 0.45,    // part bloquée la plus faible (bouclier léger)
  "maxDamageReduction": 0.7,     // la plus forte (pavois) ; le plafond de la garde, 0,75, garde de la place aux talents
  "minCostPerBlock": 4,          // endurance d'un blocage, de 4…
  "maxCostPerBlock": 20,         // …à 20
  "parryWindowShiftMs": 50       // fenêtre de parade à au plus 50 ms (un tick) de combat.parry.windowMs (150 ms)
}
```

Une garde (`ShieldGuard`) est jugée par **une seule fonction**, `ShieldGuard.Check`, appelée par le catalogue des objets et par la validation du combat (chemins `$.data.items[i].guard.damageReduction`, `$.data.combatants[0].shield.parryWindowMs`…) : part bloquée dans [0,45 ; 0,7], coût dans [4, 20], fenêtre dans [100, 200] ms, multiple du tick, d'au moins un tick et jamais au-dessus du plafond du moteur (`CombatantRules.ParryWindowCap` : 500 ms ramenées au multiple du tick ; relecture de la PR #75 : une fenêtre acceptée n'est jamais écrêtée par le moteur, même avec des règles d'essai larges). Les règles sont refusées si une borne basse dépasse la haute ou si l'écart de fenêtre sort de [0, 500] ms ; une part au-dessus du plafond de la garde (règles d'essai) reste écrêtée par le moteur. Dans un scénario (schéma 13), un personnage porte sa garde ainsi : `"shield": { "damageReduction": 0.7, "costPerBlock": 14, "parryWindowMs": 100 }` (trois champs obligatoires). Scénario livré : `scenarios/entrainement_bouclier.json` (un pavois lourd et une rondache légère contre les mêmes coups, aux mêmes instants).

## Effets d'équipement (sous-lot V1.3)

Les **armes, les boucliers (depuis les réponses de Damien du 31 octobre 2026) et les bijoux nommés** et les **paliers d'ensemble** portent des effets de combat (« effets d'équipement », [PLAN_VALLONS_SOLO.md](PLAN_VALLONS_SOLO.md#v13--effets-déquipement--armes-bijoux-ensembles-propriétés-tirées-l)) : des modificateurs, comme les talents, et des déclencheurs d'origine `equipment` (réservée depuis le lot 7.3). Ils s'ajoutent à ceux du build du personnage et, comme le reste de l'équipement, valent **à l'entrée suivante** dans un combat ([MOTEUR.md](MOTEUR.md#effets-déquipement-sous-lot-v13)).

Les règles (schéma 14) en fixent les bornes de jeu, dans le bloc `combat.equipment` (valeurs provisoires, réglées à l'équilibrage V1.8) :

```json
"equipment": {
  "maxDamageDealt": 0.25,         // damageDealt d'un modificateur : ]0 ; 0,25]
  "maxDamageTaken": 0.15,         // damageTaken : [−0,15 ; 0[ (une réduction)
  "maxHealthPercent": 0.15,       // maxHealth (pourcentage de PV maximaux) : ]0 ; 0,15]
  "maxEnduranceRegen": 3,         // endurance.regenPerSecond : ]0 ; 3]
  "maxStatusDurationMs": 1000,    // status.<id>.durationDealt : ]0 ; 1 000] ms
  "maxStrikeCoefficient": 1,      // coefficient d'une frappe de réaction, au plus 1
  "maxGain": 2,                   // gain de ressource d'une réaction, au plus 2
  "minTriggerCooldownMs": 1000,   // recharge interne d'un déclencheur d'équipement, au moins 1 s
  "allowedStatuses": []           // altérations que l'équipement peut poser (applyStatus) : aucune livrée
}
```

`allowedStatuses` (relecture de la PR #78, toujours au schéma 14 : la v0.14.0 n'était pas fusionnée) est la liste des altérations (identifiants du bloc `statuses`, sans doublon, au plus 32) que l'effet `applyStatus` d'un déclencheur d'équipement a le droit de poser. Aucun objet livré n'en pose : la liste livrée est vide, et un effet `applyStatus` d'équipement est refusé à `….triggers[i].effects[k].status` (« non admise pour l'équipement ») tant qu'une altération n'y est pas ajoutée. Une altération inconnue, un doublon ou un identifiant vide sont refusés à `$.data.combat.equipment.allowedStatuses`. Dans l'empreinte, la liste s'écrit comme les autres listes du contrat canonique 2 (`….allowedStatuses.count=n`, puis chaque élément).

Un effet (`EquipmentEffect` : source, modificateurs, déclencheurs) est jugé par **une seule fonction**, `EquipmentEffect.Check`, appelée par le catalogue des objets et par la validation du combat : source `item.…` ou `set.….<pièces>`, au moins un modificateur ou un déclencheur, au plus 4 modificateurs et 2 déclencheurs ; **clés admises** `damageDealt`, `damageTaken`, `maxHealth`, `endurance.regenPerSecond` et `status.<id>.durationDealt` (garde, parade, Charges et compétences restent aux talents et aux boucliers) ; conditions **tout ou rien** seulement (`whileGuarding`, et la nouvelle `targetStunned` : la cible du coup est étourdie, `damageDealt` seulement) ; mêmes contrôles de forme et de références que les talents (`ModifierDefinition.ValidateList`, `TriggerDefinition.ValidateList`, `ValidateReferences`), sans rang ; un `applyStatus` ne pose qu'une altération de `combat.equipment.allowedStatuses` (relecture de la PR #78). Un personnage porte au plus 40 sources, chacune une fois. Chemins : `$.data.items[i].effects.modifiers[0].add`, `$.data.sets[i].bonuses[j].effects.triggers[0].cooldownMs`, `$.data.combatants[0].equipment[1].triggers[0].effects[0].amount`…

Dans un scénario (schéma 14), un personnage porte ses effets ainsi : `"equipment": [ { "id": "item.lame_du_seuil", "modifiers": [ { "key": "damageDealt", "add": 0.1, "conditions": ["targetStunned"] } ] }, { "id": "item.amulette_de_l_aube", "triggers": [ … ] } ]`. La condition `targetStunned` n'existe que pour l'équipement : les classes (schéma 9) et les règles ne la connaissent pas. Scénario livré : `scenarios/entrainement_equipement.json` (deux Bastions, l'un équipé de la Lame du Seuil, de l'Amulette de l'aube et du premier palier de la Garde de la tour, l'autre sans, contre les mêmes coups).

## Catalogue des objets en version 4 (sous-lot V1.3)

- **Places à effets** : `slots[].effects: true` (armes, boucliers et bijoux : `weapon`, `shield` depuis les réponses de Damien du 31 octobre 2026, `neck`, `ring_1`, `ring_2`, `relic_1`, `relic_2` ; même contrôle et mêmes bornes pour toutes, sans changer de version) ; place du combat seulement, et les places d'une même sorte ont les mêmes effets.
- **Objet nommé** (`named: true`) : fait à la main (boss, quêtes, légendaires), il ne tire jamais de propriété. Un objet à effets et une pièce d'ensemble sont nommés.
- **Effets d'un objet** : `effects: { "text": "…", "modifiers": [ … ], "triggers": [ … ] }` à une place à effets ; le texte, montré au joueur, est relu par Damien. Source : l'identifiant de l'objet.
- **Ensembles** : `data.sets[]` (`id` « set.… », `name`, `bonuses[]` : `pieces` 2, 4 ou 6, croissants et au plus le nombre de pièces, `text`, `bonus` aux statistiques et/ou `effects` sans texte ; source « set.….<pièces> ») ; les pièces sont les objets qui citent l'ensemble (`set`), de 2 à 6. Les pièces portées comptent une fois chacune ; chaque palier atteint donne son bonus et ses effets.
- **Propriétés tirées** : `data.properties` : `rarities[]` (chaque rareté une fois : `count` de 0 à 8 propriétés, `scalePercent` de 1 à 1 000 %) et `list[]` (`id` « property.… », `name`, `stat` : un champ du bonus d'équipement, `min` ≤ `max` au niveau 1, `minPerLevel` ≤ `maxPerLevel` par niveau, `slots` facultatifs : sortes de place du combat). Bornes d'une propriété sur un objet de niveau requis N et de rareté R : ⌊(min + minPerLevel × (N − 1)) × échelle(R) / 100⌋ à ⌊(max + maxPerLevel × (N − 1)) × échelle(R) / 100⌋, au moins 1 ([FORMULES.md](FORMULES.md#propriétés-tirées-sous-lot-v13)). Un objet qui tire (équipement du combat, non nommé, d'une rareté qui tire) a toujours assez de propriétés possibles pour sa place ; la borne haute au niveau maximal reste sous 50 000.
- **Pire cumul de l'équipement porté** (remarque de Codex sur la PR #78) : pour chaque statistique, le validateur calcule la plus grande valeur que l'équipement porté peut atteindre (`ItemCatalog.WornBound`) : à chaque place, l'objet le plus fort (son bonus de base plus ses propriétés tirées les plus fortes sur cette statistique : au plus le nombre de sa rareté, distinctes, chacune à sa borne haute), plus tous les paliers de tous les ensembles. Au-delà de la limite du combat (`GearBonus.MaxValue`, 1 000 000, celle de `CombatSetup.Validate`), le catalogue est refusé (`LimitExceeded`), au chemin de la plus grande cause : `$.data.properties.list[k].max` (propriété tirée), `$.data.sets[s].bonuses[b].bonus.<stat>` ou `$.data.items[i].bonus.<stat>`. En défense : `Inventory.EquipTo` refuse ce qui dépasserait la limite (`InventoryRefusal.GearLimit`, rien ne change) et `Inventory.Gear()` ne rend jamais plus que la limite (une sauvegarde relue au-delà est plafonnée, avec un compte rendu).
- **Réglage du catalogue et sauvegardes** (relecture de la PR #78) : changer les bornes, retirer une propriété ou une rareté qui tire ne rend jamais une partie illisible. À la reprise, chaque instance est accordée au catalogue actuel (`ItemCatalog.Settle`) avant d'être vérifiée (`ItemCatalog.CheckInstance`) : valeur ramenée dans les bornes actuelles, propriété inconnue, impossible sur la place ou en double retirée, propriétés au-delà du nombre de la rareté retirées (les dernières), objet qui ne tire plus rendu à l'objet de base ; un compte rendu en clair (`WorldSession.Adjusted`) dit chaque changement. Une instance garde donc de 1 au nombre de sa rareté de propriétés (le tirage en donne toujours exactement ce nombre).

Livrés (valeurs provisoires, textes à relire par Damien) : quatre objets nommés à effets (la **Lame du Seuil**, l'**Amulette de l'aube**, le **Talisman du Seuil** et, depuis les réponses de Damien du 31 octobre 2026, la **Rondache du chef des bandits**), deux ensembles (**Tenue du veneur**, 4 pièces des niveaux 7 à 11 ; **Garde de la tour**, 6 pièces des niveaux 12 à 18), six propriétés (Force, Solidité, Vigueur, Souffle, Garde mystique, Ténacité) et leurs tables (0, 1, 2, 3, 4, 5 propriétés du commun au mythique depuis les réponses de Damien du 31 octobre 2026) ([MONDE.md](MONDE.md#effets-déquipement-ensembles-et-propriétés-tirées-sous-lot-v13)).

## Forge, qualité et usure (sous-lot V1.4)

- **Catalogue des objets en version 5** : `data.quality` (`superior`, `masterwork` : part du bonus de base ajoutée, de 0 à 100 %, le chef-d'œuvre au moins la qualité supérieure ; livrés : 10 et 20 %) et `data.wear` (`max` : solidité d'une pièce neuve, de 1 à 1 000 000 ; `perFullHealth` : points perdus par chaque pièce portée pour des dégâts reçus égaux aux PV maximaux, de 0 à `max` ; livrés : 100 et 10). Une qualité ajoute, pour chaque statistique non nulle du bonus de base, sa part arrondie vers le bas, au moins 1 (`ItemCatalog.QualityBonus`) ; elle se pose sur un équipement des places du combat non nommé (`TakesQuality`). Tout équipement des places du combat s'use (`Wears`), nommé compris ; ni l'Éclat du Seuil ni l'outil de métier. Le **pire cumul** (`WornBound`) compte le chef-d'œuvre dans le bonus de base de chaque place : le contrôle de la limite du combat (`GearBonus.MaxValue`) reste le même validateur unique.
- **Pièce usée à zéro** (`ItemCatalog.IsWornOut`) : elle ne donne plus son bonus (`BonusOf` rend zéro), ni ses effets, ni sa part de son ensemble, ni la garde propre d'un bouclier (celle des règles) ; elle reste portée et ne se casse pas.
- **Métiers en version 2** (`world/crafting.json`) : `quality: true` sur une recette (recette à qualité : un seul équipement qui prend une qualité) ; `forge` (`strikes` : frappes du petit jeu, de 1 à 5, livré 3 ; `superior` et `masterwork` : `base`, `perSkill`, `perLevel` en pour cent) ; `failure` (`maxLevels` : niveaux de métier au-dessus du sien qu'une recette peut demander, de 0 à 10 et sous le niveau maximal ; `percentPerLevel`, `skillReduction`, `refundPercent`) ; `repair` (`percent` de la valeur de l'objet pour une réparation complète, `minimum` en cuivre par pièce, `places` de la zone, `merchants` « merchant.… », au moins un lieu ou un marchand ; les marchands sont vérifiés contre les marchands chargés à l'ouverture de la partie). Formules : [FORMULES.md](FORMULES.md#forge-qualité-et-usure-sous-lot-v14).
- **Sauvegarde en version 11** : `quality` (« superior », « masterwork » ; normale : absente), `signedBy` (personnage signataire, obligatoire pour un chef-d'œuvre et pour lui seul), `wear` (solidité qui reste ; pleine : absente) sur une instance (place du sac ou objet porté, forme `{ "item": …, "quality": …, "wear": … }`), `crafts` (fabrications tentées) dans le personnage. L'accord avec le catalogue (qualité admise, usure sous la solidité) est vérifié à la reprise (`CheckInstance`), après l'accord au catalogue actuel (`Settle` : qualité d'un objet qui n'en prend plus redevenue normale, usure au-delà de la solidité ramenée à pleine).

## Bêtes qui se battent, bêtes qui fuient (sous-lot V2.4)

**Règles en schéma 15, contenu 0.16.0** (une version 14 est refusée sans migration) : bloc obligatoire `combat.infighting` avec `damageReduction` (dans [0, 1], **0,5** livrée) : les dégâts directs d'une créature (assaillant) sur une créature d'une **autre équipe** sont réduits d'autant, combinés aux autres réductions de l'impact comme un modificateur de dégâts subis (formule B2, même plafond) ; jamais sur un impact paré, jamais pour un personnage. Raison : un combat de bêtes dure assez pour qu'on le voie et qu'on s'en mêle.

## Cases et repère de la région (sous-lot V2.25.3)

Premier sous-lot de la grande carte ([PLAN_GRANDE_CARTE.md](PLAN_GRANDE_CARTE.md), § 2.1 et § 7, étape 1). **Zones en schéma 13** : bloc facultatif `data.region`, le repère et la grille de la région. **Données seulement** : le moteur, la simulation, les journaux et les sauvegardes n'en dépendent pas (les secteurs de simulation viennent au V2.26).

```json
"region": { "origin": [-1908, -1614], "columns": 32, "rows": 24 }
```

| Champ | Bornes |
|---|---|
| `origin` | coin sud-ouest `[x, z]`, en mètres **entiers**, à au plus 100 000 m de zéro |
| `columns`, `rows` | nombre **pair** (des secteurs entiers), de 2 à 64 |

- **Constantes du schéma 13** (`RegionGrid`) : case carrée de **128 m**, secteur de **2 × 2 cases (256 m)**. Case `c<colonne>_r<rangée>` (colonne 0 à l'ouest, rangée 0 au sud, sans zéro de tête) ; secteur `s<colonne>_<rangée>` sur deux chiffres (`s07_06`).
- **Un seul repère** : celui de la zone (x vers l'est, z vers le nord, en mètres) ; rien ne bouge. Les Vallons (contenu inchangé, 0.17.0) passent en schéma 13 avec le repère du plan : de (−1 908, −1 614) à (2 188, 1 458), 32 × 24 = 768 cases, 16 × 12 = 192 secteurs ; l'aire actuelle ([−100, −70] à [140, 100]) tient entière dans `c14_r12`, `c15_r12`, `c14_r13`, `c15_r13`, le secteur `s07_06`.
- **Case d'un point** : chaque case contient ses bords ouest et sud (un point sur le bord entre deux cases est dans celle de l'est ou du nord) ; les bords est et nord de la région sont dans la dernière case. **Rectangle fermé** (lieu, boîte d'un obstacle) : toutes les cases qui contiennent un de ses points au sens de la case d'un point, bords est et nord compris (revue Codex de la PR #148 : un lieu dont le bord est tombe sur x = 140 touche aussi `c16_r12` et `c16_r13`, comme le point de ce bord). **Route** : réunion des cases de la boîte fermée de chaque tronçon, donc aussi la case de chaque sommet, même posé sur une frontière (comptage par excès pour un tronçon en biais, voulu). **Porte, point sûr, population, place de nuit** : la case de leur point. Calcul entier sur la virgule fixe, sans flottant.
- **Validation** (validateur unique, erreurs au chemin précis) : `$.data.region.origin` (manquant, non entier, trop loin), `$.data.region.columns` et `.rows` (manquants, impairs, hors bornes), `$.data.region` (aire praticable ou obstacle du scénario hors de la région ; région en schéma 12 et avant), champ inconnu refusé (`$.data.region.cellSize`).
- **Bornes relevées pour une zone à région** : au plus **2 048 lieux**, **256 portes**, **1 024 routes** de **128 points** ; et **par case** : au plus **64 lieux**, **16 portes**, **32 routes** qui la touchent ; l'erreur porte sur le premier élément qui fait déborder la case, avec son nom (`$.data.places[70]` : « case c14_r12 : plus de 64 lieux »). Une zone **sans région** garde les bornes d'avant (64 lieux, 16 portes, 32 routes de 32 points). Points sûrs (32), populations (256) et zones reliées (64) inchangés (relevés avec les sous-lots qui en ont besoin : V2.28, V2.45).
- **Découpage** (`RegionCutting.Cut`) : fonction pure de la zone, toutes les cases rangées (par rangée puis par colonne) avec leurs obstacles, lieux, points sûrs, portes, routes, populations (place de départ) et places de nuit. **Points d'intérêt** d'une case (provisoire, plan § 4.5) : lieux, points sûrs, portes et populations.

Outil : `eds carte` ([ci-dessous](#commande)).

```json
"carried": { "health": 300, "endurance": 40, "enduranceRegenMs": 500, "resonance": 30, "rampartCharges": 2,
             "globalCooldownMs": 500, "cooldowns": { "skill.bastion.heurt_de_bouclier": 3000 }, "consumableCooldownMs": 0 }
```

Tous les champs sont facultatifs (absent : plein ou prêt) ; durées en ms, multiples du tick, comptées depuis l'arrivée. ## Secteurs de simulation et territoire (sous-lot V2.26, PR b)

**Zones en schéma 14** (13 à 7 encore lues) : `territory` facultatif sur une population, rayon en mètres autour de sa place de départ ; une créature engagée qui en sort **lâche** comme pour la laisse (elle s'en va, ni mort ni butin, une vie calme la remplace chez elle ; `PopulationEventKind.Leashed`). Bornes : ]0, 256] m ; sans région, au plus **40 m** ; avec une région, au plus la distance de sa place au **bord intérieur** de son secteur (bord qui passe dans l'aire de la zone : au-delà, un autre secteur) plus la **marge de 32 m** (`ZoneValidator.InnerEdgeDistance`). Dans une zone à région en schéma 14, chaque créature peuplée part d'au moins **8 m** d'un bord intérieur de son secteur. Un départ à 8 m et un territoire de 40 m ne dépassent jamais la marge. Les Vallons (cœur seul, aucun bord intérieur) restent en schéma 13 et se lisent aussi en 14 sans changement.

**Hôte des secteurs** (`EdS.World/Sectors.cs`) :

- `SectorMap` : secteurs de 256 m de la grille de la région ; espace d'un secteur = son carré **plus 32 m** de chaque côté, coupé aux bornes de l'aire ; obstacles de l'aire qui touchent cet espace ; créatures dont la place de départ est dans le secteur (une seule appartenance, `SectorMap.OwnerOf` : un point posé sur le bord ouest ou sud d'un secteur qui ne touche pas l'aire revient à son voisin simulé ; test de propriété). Secteur du **cœur** = celui du point d'entrée de la zone : si l'aire tient dans son **carré, sans la marge** (revue Codex de la PR #150, 7e tour : tenir dans sa marge seulement laisserait un voisin posséder une partie de l'aire ; une créature serait simulée deux fois), sa simulation est **l'aire elle-même** (même combat, même graine, mêmes clés `zone.vallons/<session>/death/<id>`) ; les Vallons d'aujourd'hui ne changent donc pas (test : même journal que la zone d'avant sur 200 ticks). Un autre secteur : graine tirée de l'empreinte de son nom et de sa session (FNV-1a, mêlée à celle de l'aire), clés `zone.vallons/s08_05/<session>/death/<id>`.
- `SectorWorld` : un ou plusieurs joueurs. **Activation** : un secteur s'ouvre (session neuve, au tick du monde courant) dès qu'un joueur est à moins de **96 m** de son carré ; il se ferme après **60 s** sans joueur aussi proche (son registre revient au monde). Tous les secteurs ouverts avancent **au même tick du monde**, dans l'ordre de leurs noms. **Passage** : à plus de **8 m** au-delà du bord de son secteur (hystérésis) et hors de toute rencontre, le joueur part en fin du tick t (`leave`) et arrive au tick t + 1 dans le voisin, avec son **état de combat** (`CombatEngine.Carried`, objets de soin restants), sa place (la plus proche libre, anneaux de 0,5 m), son orientation et sa marche en cours ; ordre : secteur de départ, puis joueur. Une identité déjà servie dans la session d'arrivée devient `<joueur>_p<n>` (jamais réutilisée). **En combat**, il reste dans son secteur jusqu'au bout de la marge ; là, les créatures de la rencontre lâchent (`ZonePopulations.Release`, ou départ simple d'une créature hors population) et il passe au tick suivant sans rencontre. Sous-lot V2.28b (4) : tant qu'il est engagé au-delà de l'hystérésis, chaque créature de la rencontre arrivée elle-même au bout de la marge lâche (avant, des créatures arrivées avant lui au bout de la marge l'empêchaient d'y arriver : il restait coincé dans son secteur). Revue Codex de la PR #150 : pas de départ sans place, sans identité libre ni endroit libre dans le secteur d'arrivée ; les arrivées déjà programmées au même tick (réapparitions, autres passages) tiennent leur place ; une arrivée impossible ou refusée malgré tout ramène le joueur dans son secteur de départ avec son état (ou réessaie au tick suivant) : il n'est jamais perdu. Le cœur rouvert après une fermeture prend une session nouvelle (clés au format du cœur, « zone.vallons/<session>/death/<id> », graine tirée du nom et de la session, journal distinct) ; sa première ouverture reste exactement la zone. Entrées et sorties de joueurs appliquées au début du tick suivant, dans l'ordre des identifiants : rien ne dépend de l'ordre des messages (test à deux joueurs), ni, pour un secteur, du nombre de secteurs ouverts ailleurs (test : même journal du secteur ouest avec ou sans activité à l'est).
- **Fin de session, entrée, reprise, registre** (revue Codex de la PR #150, 2e et 3e tours) : un secteur dont la session atteint sa durée (`durationMs`) **repart** au même tick du monde dans une session nouvelle (`SectorEventKind.Renewed`, numéro dans `Other`) ; ses joueurs vivants y arrivent avec leur état et leur marche, un joueur mort garde sa dernière vue (`ViewOf`). La première entrée dans la région prend la place libre la plus proche (arrivées programmées comprises) ; sans place ni identité, le joueur attend (`IsWaiting`) et réessaie à chaque tick. Un passage sans place ni à l'arrivée ni au départ devient une **reprise** sans combattant (`IsResuming`), gardée jusqu'à un placement réussi. Une sortie au tick d'une arrivée programmée fait aussi partir ce combattant. À la fermeture (ou au renouvellement) d'un secteur, les **clés de mort de sa session** sont purgées du registre du monde (plan § 2.4) ; les autres clés (faits persistants) sont gardées. **Budgets et populations** (4e tour) : l'arrivée et la marche qui continue ont leur budget (`combat.limits.maxCommands`, `maxPendingEvents`) réservé avant l'arrivée (`CombatEngine.HasRoomToJoinWith`, refus atomique) ; un départ ou une sortie dont la commande est refusée n'a pas lieu (nouvel essai au tick suivant). Le prédicat de présence (`wanted` de `SectorWorld` et `SectorWorld.For`, au tick du monde : heures, temps, nuits rares) est passé aux populations de chaque secteur, qui comptent toutes les populations dont la place est dans le secteur ; même comportement que l'hôte d'une zone (`ZonePopulations.Step`), sans prédicat : jamais voulues. Au passage et au renouvellement, le joueur garde son **bonus d'équipement courant** (`CombatantView.Gear`, changé en jeu par une commande `gear`) ; tout refus du moteur (`ArgumentException` ou `InvalidOperationException`, budget compris) d'une arrivée, d'un départ, d'une sortie ou d'un lâcher ne change rien et réessaie au tick suivant (5e tour). Le compteur d'inactivité d'un secteur passe d'une session à la suivante au renouvellement : un secteur abandonné se ferme à 60 s même si sa session est plus courte (6e tour). Chaque session nouvelle d'un secteur (ouverture, réouverture, renouvellement) tire son décor et ses créatures du **registre courant** (`ZoneSetups.For` sur `SectorWorld.Consumed`, avec `SectorWorld.For`) : un passage ouvert pendant le monde n'a plus son obstacle à la session suivante, comme dans [MONDE.md](MONDE.md) (8e tour). **Tick tout ou rien** (9e tour) : avant toute modification, `SectorWorld.Step` vérifie que le registre du monde entier a la place de tout ce que le tick peut y ajouter (`NextTickRegistryNeed` : borne du registre, morts possibles des secteurs ouverts, une clé par créature de l'aire et par joueur présent ou annoncé) et que les clés de mort sont au format ; sinon il refuse le tick entier (`InvalidOperationException`), aucun secteur n'avance. Une entrée est validée à l'annonce (`Enter` : refus définitif avec son diagnostic, par exemple des PV emportés au-delà du maximum) ; seul le manque de place la met en attente ; un joueur annoncé peut renoncer (`CancelEnter`). Une arrivée de passage refusée par la validation est définitive (`RefusalOf`), le manque de place reste temporaire. **Commandes de l'aire** (10e tour) : un secteur découpé ne garde que les commandes de ses acteurs ; une commande dont la cible appartient à un autre secteur est **retirée** (sa cible n'existe pas dans la session). Un identifiant de joueur est refusé à l'entrée si la clé de mort de l'une de ses identités possibles (`<id>_p<n>`, secteur et session les plus longs) dépasserait 200 caractères ; un joueur refusé pour de bon n'est pas renouvelé. **Références entre combattants au découpage** (11e tour) : les seules d'un combat sont la cible d'un assaillant et l'acteur et la cible d'une commande (les trêves lient des équipes, les groupes d'errance un nom : un groupe sans son chef dans le secteur suit le premier chef présent ou erre sans chef ; les populations leur créature). Une cible dans un autre secteur est **retirée** à un assaillant à comportement (il choisit le plus proche) et à un assaillant sans comportement dont toutes les attaques visent tous les ennemis ; un assaillant sans comportement à attaque à cible unique est lié à sa cible : il n'est **pas simulé** dans ce secteur (ni sa population, ni ceux qui le visaient, de proche en proche), de proche en proche. La réapparition d'une population suit **la même règle** (`CombatantReferences.Adapt`, partagée avec le découpage ; `CombatantReferences.Keeps` pour les commandes) : cible absente retirée (bête à comportement, ou sans attaque à cible unique) ; une bête liée à une cible absente ne revient pas (sa vie s'arrête au lieu d'être réessayée sans fin). Chaque secteur découpé d'une aire valide passe la validation (test de propriété). **Populations d'un secteur** (12e tour) : une seule source, les combattants de la session découpée (chaînes de cibles comprises) : la créature d'une population y est, ou elle est absente de l'aire de la session (retirée au début : rare de la nuit, hors de ses heures ou de son temps). Garde : une population présente au début dont la créature manque à la session fait refuser l'ouverture du secteur, avec son diagnostic, avant toute modification.
- **Partie solo** : depuis le V2.28b, la session d'une zone à région de la partie solo (`WorldSession`, `AdventureSession`) est tenue par l'hôte des secteurs, à parité tant que l'aire tient dans le secteur du cœur ([plus bas](#partie-solo-sur-lhôte-des-secteurs-sous-lot-v228b-première-partie)). **Pas encore** : le passage du personnage solo d'un secteur à l'autre (suite du V2.28b), montures, compagnons et caravanes (lots des lieux) ; les altérations ne passent pas (limite du moteur 0.31.0). Le serveur du lot 10 (`EdS.Net`) reste une salle par combat ; l'hôte des secteurs est fait pour lui (plusieurs joueurs, ordre stable), branché au lot 13.

## Partie solo sur l'hôte des secteurs (sous-lot V2.28b, première partie)

[Plan](PLAN_GRANDE_CARTE.md#23-ce-que-fait-chaque-côté-recommandation) § 2.3 : « en solo, la partie joue le rôle de l'hôte ». Aucun format ne change (ni sauvegarde, ni zone, ni journal, ni moteur).

- **Qui est tenu par l'hôte** (`WorldSession.OnSectors`) : la session d'une zone **à région** dont l'aire tient dans le carré du secteur du cœur (`SectorMap.HomeHoldsArea` : les Vallons d'aujourd'hui). Restent une session de zone comme avant : une zone sans région (un intérieur, un fichier en schéma 12), une session sans zone du monde, et une aire à plusieurs secteurs tant que le passage du personnage solo n'est pas fait (suite du V2.28b).
- **Sessions qui naissent et renouvellement** (revue Codex de la PR #156, 1er tour) : la réserve des naissances de `NextTickRegistryNeed` compte les créatures de la **définition entière** de la zone, et non l'aire filtrée par l'heure et le temps du départ (une session renouvelée la nuit a plus de créatures qu'une aire de crépuscule). Le renouvellement d'une session terminée est **atomique** : la session nouvelle est préparée d'abord (sur le registre qu'aura le monde après la fermeture), la place exacte au registre de tous les renouvellements du tick est vérifiée (créatures à l'heure du renouvellement, une clé par joueur), et seulement ensuite l'ancienne est fermée ; un refus ne change rien. Test : départ au crépuscule, renouvellement de nuit près du plafond : refusé entier, ou accepté entier, jamais partiel (il échoue sans la correction). Autres bornes relevées : les marges de place au registre de la partie solo (conversion d'une sauvegarde d'avant V1.8, découverte d'un point sûr, nuit rare) comptent l'aire du départ ou les combattants présents ; elles ne servent qu'à décider d'inscrire une clé, et un manque de place y aboutit au refus entier du tick par la session (`Zone.Step`), jamais à un tick partiel.
- **Allocations** (relecture indépendante de la PR #156) : le tick de la partie n'alloue rien pour appeler l'hôte (délégués et liste gardés d'un tick à l'autre) ; dans l'hôte, les étapes rares (renouvellement, attente, reprise, passage, fermeture) sont gardées par un balayage simple, et une aire à un seul secteur saute les ouvertures et les passages. Mesure : 519 583 octets par tick sur l'hôte, 518 799 pour la session de zone (784 de plus, 0,15 %).
- **Même partie** : le personnage entre **avec la session** de son secteur (`SectorWorld.EnterAtStart` : il fait partie de la simulation de départ, en-tête du journal compris, à sa place exacte, comme le personnage d'une session de zone) ; l'aire est celle du moment (heure et temps du monde : `SectorWorld.For(…, start)`, créatures à heures ou à temps absentes d'emblée hors de leurs heures) ; même numéro de session, même graine, même registre, mêmes clés (« zone.vallons/3/death/loup1 »), mêmes vies des populations dans le même ordre. Le tick garde son ordre : session, récompenses de la partie, populations (`SectorWorld.Step(…, afterZone, reserved)` : crochet entre le tick d'une session et celui de ses populations, places de combattants gardées pour les formes des chefs et les événements). Tests : même journal **octet par octet**, mêmes événements de la partie, mêmes empreintes et même sauvegarde que la session de la même zone sans région, de jour, de nuit, pendant l'attaque du hameau et la faille, avec un loup tué puis revenu (`V228bSoloSecteursTests`).
- **Fin de session** : sous la partie solo, l'hôte ne renouvelle pas une session terminée (durée d'une heure) : plus rien n'avance et la partie reprend au dernier point sûr, comme avant. Le renouvellement sans coupure (un secteur qui repart au même tick du monde) reste celui de l'hôte à plusieurs joueurs ; la partie solo le prendra avec le passage d'un secteur à l'autre.
- **Registre** : la place exigée par un tick (`SectorWorld.NextTickRegistryNeed`) est **exacte** quand aucune session ne peut naître avant le tick des secteurs (ni entrée annoncée, ni joueur en attente d'une place ou en reprise, ni session terminée à renouveler) : registre et morts possibles du tick, comme une session de zone ; sinon elle compte en plus toutes les créatures de l'aire et une clé par joueur qui arrive. Avec un seul secteur ouvert, aucune session à naître, aucune sortie demandée **et un registre du monde inchangé depuis l'ouverture de ce secteur**, l'hôte ne refait pas le précontrôle de la session (`Zone.Step` : même borne, mêmes clés de mort, rien ne bouge si elle refuse). Relecture indépendante de la PR #156 : dès qu'un voisin s'est fermé (ses clés reprises par le monde, absentes de la recopie de la session restante), la borne de la session n'est plus celle du monde et le précontrôle du monde est fait (tick refusé entier ; test sur une aire à deux secteurs, près du plafond). Tests de la borne elle-même, pas seulement de sa formule : avant chaque tick elle majore le registre d'après (entrée, mort, passage, sortie, fermeture) ; remplie jusqu'à elle, le tick est accepté sous le plafond, une clé de plus et il est refusé sans rien changer.
- **Secteurs sauvegardés** : inchangés par la partie solo (`sectors` rendu tel quel) tant qu'un seul secteur est joué.

## Passage du personnage solo d'un secteur à l'autre (sous-lot V2.28b (2), première partie)

[Plan](PLAN_GRANDE_CARTE.md#24-secteurs-marge-et-passage-dun-secteur-à-lautre-rupture-retenu-par-damien-le-11-novembre-2026) § 2.4. Aucun format ne change.

- **Qui** : une zone à région dont l'aire couvre plusieurs secteurs est tenue par l'hôte des secteurs **si elle n'a ni chef ni événement du monde** (ils seront liés à leur secteur dans une partie suivante) ; sinon elle reste une seule session, comme avant. Les Vallons livrés (cœur seul) ne changent pas.
- **Passage** : la partie (`WorldSession`) suit le personnage : `Zone` est la session du secteur où il est, `CombatantId` son identité dans cette session (la sienne, ou `<personnage>_p<n>` dans une session où elle a déjà servi), `Sector` son secteur, `Passages` le nombre de passages. Les commandes vont au moteur et à l'identité du moment. Au passage, les relevés pris sur son combattant (dégâts reçus pour l'usure, gestes pour le tutoriel) repartent du combattant d'arrivée : rien n'est perdu ni compté deux fois (test qui échoue sans cela).
- **Registre commun** : `WorldSession.Registered` cherche une clé dans le registre du monde et dans chaque session ouverte (`SectorWorld.IsConsumed`) : un point sûr découvert dans un secteur l'est dans les autres, sans seconde annonce (test qui échoue sans cela). La place restante (`WorldSession.RegistryRoom`) est la plus petite de celle de la session et de celle du monde entier (`SectorWorld.RegistryRoom`, d'après la borne du registre).
- **Créatures et récompenses** : chaque secteur a ses populations (`SectorWorld.PopulationOf`, `CurrentOf`, `ReturnedFromDeath`). Les récompenses (expérience, butin, objectifs « vaincre ») viennent des morts de la session du personnage, une fois par tick ; dans un autre secteur, seule la nuit d'une créature rare tombée là est retenue (il ne peut l'avoir frappée). Clé de mort d'un autre secteur : `zone.<nom>/<secteur>/<session>/death/<id>`.
- **Sauvegarde** (aire à plusieurs secteurs) : session du monde, registre du monde et de chaque session ouverte, dernière session de chaque secteur (`sectors`), point de reprise et son secteur. La partie reprise rouvre d'abord le secteur du point de reprise, sous sa session suivante.
- **Ordre au passage** (revue Codex de la PR #157, 1er tour) : relever, propager, puis remplacer. Ce que le combattant sortant a reçu et fait depuis le dernier relevé, **son dernier tick compris** (dégâts pour l'usure, coups, blocages et parades pour le tutoriel), est gardé comme écart et compté au relevé suivant avec ceux de l'arrivant (`WorldSession.Rebased`). Un bonus d'équipement qui change quand le sortant n'est plus là (bonus expiré au tick du départ) n'est pas perdu : la synchronisation reste en attente et s'applique au combattant d'arrivée (l'hôte le place avec le bonus du sortant). Le tick d'un événement d'un autre secteur (mort d'une créature rare) est converti en tick du monde avec la session de **ce** secteur, jamais avec celle du personnage. Les événements de population des autres secteurs rendus dans `SessionStep.Population` gardent un tick relatif à leur session ; aucun appelant ne s'en sert.
- **Une seule horloge** (revue Codex de la PR #157, 2e tour) : l'état que la partie garde d'une session de secteur à l'autre est daté en ticks du **monde**, jamais en ticks d'une session (qui repart de zéro à chaque ouverture) : les échéances de repousse des nœuds de récolte (`Workshop.IsReady`, `WorldSession.IsNodeReady`, non sauvegardées) ; la nuit d'une créature rare (ci-dessus). Recensé sans autre cas : les bonus actifs comptent leurs ticks restants (relatifs, sauvegardés en ticks restants), les marchands et les fêtes comptent en jours du monde, la Guilde en jours du monde. L'affichage du combat (cible, annonces, pont temps réel) suit le moteur de la session et sera rebranché à chaque passage avec l'aventure (V2.28b (2b)).
- **Sans combattant** (relecture indépendante de la PR #157) : en attente d'une place, en reprise d'un passage refusé des deux côtés, refusé pour de bon ou mort dans une session terminée (`SectorWorld.IsFollowed` faux), la partie garde sa dernière session et sa dernière identité et chaque tick va à son terme ; elle retrouve le personnage au tick où l'hôte le replace.
- **Réserve du registre** (relecture indépendante de la PR #157) : toute inscription de la partie (compétences données, découverte d'un point sûr, nuit d'une créature rare, récompenses d'un chef) garde la place des morts possibles de **toutes** les sessions ouvertes (`WorldSession.DeathReserve`, `SectorWorld.OpenCombatants`), comme la borne du tick du monde ; une seule fonction. Avec le cœur seul, c'est la réserve d'avant. Sinon une découverte pouvait remplir le registre et bloquer le monde pour toujours (test à deux secteurs ouverts près du plafond).
- **Voisin impossible à ouvrir** (sauvegarde abîmée : sa session suivante dépasserait le temps du monde) : il reste fermé, sans rien changer ; le personnage ne peut pas y passer et le tick va à son terme.
- **Pas encore** : événements du monde et cicatrices liés à leur secteur (V2.28b (2c) ; les chefs le sont, ci-dessous) ; affichage de plusieurs secteurs dans Unity (V2.28b (3)). L'aventure et le pont temps réel suivent un passage depuis le V2.28b (2b) (ci-dessous).

### Aventure et pont temps réel à chaque passage ; session renouvelée sans coupure (sous-lot V2.28b (2b))

Aucun format ne change (sauvegarde, zone, journal, moteur, règles) ; un texte de plus (`text.ui.sector_refused`).

- **Pont temps réel** (`RealtimeCombat`) : après chaque pas, il demande où joue le personnage (`CombatBinding` : simulation, moteur, identité) et se rebranche s'il a changé (passage de secteur, session renouvelée), dans l'ordre **relever, propager, remplacer** : les retours du dernier tick de l'ancien moteur (dégâts, blocage, parade, morts) sont collectés avant de le quitter ; la garde tenue, la marche voulue (le moteur d'arrivée a reçu la marche en cours), les retours non lus et le temps accumulé restent ; puis simulation, moteur, identité (`PlayerId`, `bastion_p<n>` au retour dans une session où il a servi), décor de la vue et références des compteurs sont remplacés (rien n'est compté deux fois). La cible ne passe pas (identités d'un autre moteur) : elle repart du plus proche ennemi en vue. `Rebinds` compte les rebranchements ; le temps du pont (`Tick`) est celui du moteur du moment. Relecture indépendante de la PR #158 : les retours du combattant d'arrivée comptent depuis zéro (après un renouvellement, son premier tick est déjà joué quand le pont se rebranche ; il est rendu) ; tant que le personnage n'est pas encore là (arrivée d'un passage au tick qui vient, attente d'une place), les demandes ponctuelles (compétence, parade) sont gardées pour son premier tick de présence au lieu d'être perdues. Le moteur ne prend aucune commande d'un combattant pas encore arrivé : au tick de son arrivée (passage comme renouvellement), il joue sans garde ni compétence ; la garde tenue reprend au tick suivant (un tick de 50 ms).
- **Aventure** (`AdventureSession`) : toutes ses lectures du moteur (position, halte, porte, objets de soin, ennemis proches, ennemi engagé, musique du chef, arrivée refusée) passent par l'identité du moment (`WorldSession.CombatantId`), plus par `PlayerId` (l'identifiant du personnage). La carte et les trajets des PNJ sont refaits quand l'espace de la session du moment change (passage de secteur ; `CombatDisplay.SameSpace` : mêmes bornes, mêmes obstacles), pas pour une session renouvelée sur le même espace. Unity refait les corps de l'arène à chaque rebranchement (`EdsGame`, sans fondu) ; l'affichage de plusieurs secteurs à la fois reste au V2.28b (3).
- **Session renouvelée sans coupure** (`WorldSession.RenewsSessions`) : sur l'hôte des secteurs et pour une zone **sans chef ni événement du monde**, une session terminée (durée atteinte, ou budget du moteur dépassé) n'arrête plus la partie : au tick suivant, l'hôte ouvre la session suivante du secteur au même tick du monde, le personnage y arrive avec son état (position, PV, état emporté, objets de soin, marche) et la partie le suit (`Renewals`). Le pont ne se termine pas avec la session (`IsFinished`) et ne lui soumet plus de commande. Près du plafond du registre (borne de l'hôte, tous les secteurs ouverts), le renouvellement n'est pas tenté si l'hôte le refuserait (relecture indépendante de la PR #158) : la session terminée mène alors à la reprise au dernier point sûr, comme avant, sans tick refusé (exception) à chaque tick. Un personnage mort quand sa session se termine n'est pas suivi dans la suivante : la partie reste vaincue et l'aventure reprend au dernier point sûr. Une zone qui a un chef ou un événement du monde (les Vallons livrés) garde le comportement d'avant : fin de session, reprise au dernier point sûr (V2.28b (2c)).
- **Ordre des rappels de l'hôte** (revue Codex de la PR #158, 1er tour) : quand la session du personnage change pendant le tick de l'hôte, avant le pas des sessions (session renouvelée, arrivée après une attente), la partie le suit dès le rappel qui suit le pas de sa session (`AfterSector`), avant les objets de soin, les bonus et les récompenses du tick : aucun rappel ne lit une session périmée. Un passage et une reprise se décident après le pas des sessions (arrivée au tick suivant) : ils sont suivis après le tick de l'hôte, avant les découvertes, les métiers et le reste du tick de la partie. Les nuits des créatures rares d'un autre secteur sont datées avec la session de ce secteur. **Bonus porté par l'arrivée** : le bonus d'équipement voulu (bonus actifs) est confié à l'hôte (`SectorWorld.CarryGear`) à chaque synchronisation ; toute arrivée du personnage (passage, renouvellement, reprise, attente d'une place) le porte dès son premier tick, au lieu de celui du combattant précédent. Un bonus qui finit au dernier tick d'une session, au tick d'un passage ou autour dure ainsi exactement son temps (règle « Fini » de [MONDE.md](MONDE.md)) ; avant, il durait un tick de trop chez l'arrivant, au passage comme au renouvellement.
- **Relevés à l'arrivée** : les relevés de la partie (dégâts reçus pour l'usure, coups, blocages, parades pour le tutoriel) repartent de **zéro** pour le combattant d'arrivée, toujours nouveau, moins les écarts du sortant. Au passage, rien ne change (l'arrivée est au tick suivant, ses compteurs sont à zéro) ; au renouvellement, il arrive au début du tick, déjà joué quand la partie le suit : ce qu'il aurait reçu ou fait à ce premier tick serait sinon perdu. Aucun cas constructible avec le contenu actuel (une attaque ne frappe pas au tick de l'arrivée) : c'est une précaution.
- **Passage refusé pour de bon** (arrivée invalide : `WorldSession.SectorRefusal`) : le personnage n'a plus de combattant et ne sera plus replacé ; l'aventure le traite comme une arrivée refusée (`Stranded`, message « Le passage vers cette partie de la région est impossible : tu reprends au dernier point sûr. », dit une fois, même hors d'un tick) et la reprise (`Continue`) rouvre une session au dernier point sûr. Les autres états sans combattant (attente d'une place, reprise d'un passage, reprise pendant un renouvellement) laissent avancer chaque tick du pont sans exception, et il retrouve le personnage quand l'hôte le replace.
- **Mesures** (14 novembre 2026, même outil sur `main` (955e426) et sur cette PR, passes alternées, 3 000 ticks après 100 de mise en route, machine partagée chargée, charge de 10 à 25) : octets alloués par tick sur les Vallons, **partie seule** (`WorldSession.Step`) : hôte 519 014 (`main`) et 519 014 à 519 094 (PR), session de zone 518 158 et 518 158 à 518 238 ; **pont** (`RealtimeCombat.StepOnce`, la partie et l'affichage portable) : hôte 790 478 (`main`) et 790 478 à 790 558 (PR, suivi compris), session de zone 789 622 et 789 622 à 789 702. Aucune hausse : les quelque 790 ko du pont et les quelque 519 ko de la partie seule (mesure de la PR #156) sont deux mesures différentes ; l'écart d'environ 271 ko par tick vient du pont, et il est le même sur `main`. Temps par tick de 0,5 à 4 ms selon la charge, sans écart attribuable. Passage d'un secteur à l'autre (Vallons à deux secteurs, montage d'essai) : tick du passage d'environ 0,9 Mo alloués par la partie seule (hôte, V2.28b (2a)), 1,03 Mo avec le pont (rebranchement : vue et références des compteurs) ; carte et trajets refaits ensuite en 0,4 à 0,7 ms et 88 à 124 ko ; temps du tick du passage de 3 à 23 ms à cette charge (bruit de la machine trop fort pour conclure). Zone d'essai renouvelée tous les 40 ticks : 0,06 ms et 38 900 octets par tick, renouvellements compris.

### Chefs liés à leur secteur (sous-lot V2.28b (2c), première partie)

[Plan](PLAN_GRANDE_CARTE.md#25-créatures-qui-suivent-le-joueur-recommandation) § 2.5. Aucun format ne change (sauvegarde, zone, journal, moteur, règles) ; une règle du validateur de plus ; deux sortes d'événement de chef de plus (`BossEventKind.Returned`, `Carried`, sans message).

- **Validateur** (zone à région, schéma 13 compris) : toutes les formes d'un chef sont dans le secteur de sa première forme, à au moins 8 m de ses bords intérieurs (`$.data.boss.forms[i]`, `$.data.chiefs[n].forms[i]`) ; comme une population, un chef part de l'intérieur de son secteur. Les chefs des Vallons livrés sont tous dans le cœur.
- **Qui est tenu par l'hôte** : une zone à plusieurs secteurs **avec des chefs** l'est désormais (et, depuis la suite du (2c), avec des événements du monde), et elle renouvelle ses sessions sans coupure. **Changement de comportement** : une zone au seul secteur du cœur, avec un chef et sans événement du monde, renouvelle aussi sa session sans coupure (avant, elle reprenait au dernier point sûr) ; aucune zone livrée n'est dans ce cas.
- **Un chef vit dans la session de son secteur** (`BossFight.Sector`, `Session`). Ceux du secteur où entre le personnage arrivent avec la session, comme avant ; les autres arrivent avec chaque ouverture ou réouverture de leur secteur, à leur première forme (rappel de l'hôte `SectorWorld.OnOpened`, avant le premier tick de la session et **avant toute mutation de l'hôte** : s'il lève, le tick est refusé entier). Un secteur fermé laisse son combat en sommeil ; une première forme refusée par le moteur laisse le chef absent de cette session (rien ne lève).
- **Décision de Damien du 14 novembre 2026 (« AAA », 1)** : un chef qui poursuit le personnage hors de son secteur lâche au bout de la marge de 32 m (comme toute créature) ; la même forme revient à sa place, tous ses PV, sous une identité nouvelle (`Returned`).
- **Décision de Damien du 14 novembre 2026 (« AAA », 2)** : au renouvellement de la session de son secteur, le combat continue tel quel (`BossFight.Continue`) : même phase, la forme du moment arrive dans la session nouvelle à sa place avec son état emporté (PV, ressources ; `Carried`) ; une forme à venir arrive au premier pas ; un chef vaincu le reste (aucune forme, aucune seconde victoire) ; une récompense en attente (sac ou registre plein) est gardée. Revue Codex de la PR #159 (1er tour) : l'état emporté (place, PV, ressources) est gardé jusqu'à l'**arrivée effective** de la forme et réutilisé à chaque nouvel essai, à la place libre la plus proche de la sienne (règle d'arrivée du joueur, `SectorWorld.FreeSpotOf`) : une créature qui revient sur cette place au renouvellement ne la fait plus repartir de sa place de départ, PV pleins ; `Carried` n'est rendu qu'à l'arrivée. Revue Codex de la PR #159 (2e tour) : l'arrivée se lit sur un fait du moteur (`CombatantView.ArrivedTick`, lecture seule, déjà dans l'instantané) : l'état emporté est consommé dès qu'elle a eu lieu, même si la forme est morte avant que le combat l'examine (le moteur fait les arrivées puis les dégâts), et avant tout changement de phase ; la forme suivante n'en hérite jamais. Le personnage suit déjà la même règle (son arrivée est consommée s'il est là, mort ou parti). Revue Codex de la PR #159 (3e tour), **forme emportée en attente** (état nouveau : emportée, pas encore arrivée, `BossFight.IsCarrying`), traitée partout : **recherche de place** : l'arrivant est une créature, le personnage lui est solide (`SectorWorld.FreeSpotOf(…, character: false)` ; les passages du joueur gardent leur règle) ; **borne du registre** : comptée à la naissance de la session suivante, où elle est réessayée avant le premier tick (`JoinsAtBirth`, donc `NextTickRegistryNeed` et `RenewalNeed`), et au tick qui suit son nouvel essai dans la session (elle est alors au moteur) ; **places gardées** : une place dans la session de son secteur (`FormsToCome`, arrivée à venir) ; **sauvegarde** : non sauvegardée (une partie reprise est une vraie réouverture : le chef recommence) ; **vue** : son identité reste celle du combat (`BossForms`), sans combattant au moteur tant qu'elle n'est pas arrivée ; **secteur fermé** pendant l'attente : combat en sommeil, recommencé à la réouverture. Les autres arrivées emportées (le personnage : reprise gardée jusqu'au placement réussi, V2.26) suivent déjà cette règle ; les populations ne portent pas d'état.
- **Références des formes** (revue Codex de la PR #159, 4e tour) : toute arrivée d'une forme (premier départ, forme suivante, emportée, retour) et d'une créature d'événement passe par la règle unique du découpage et des populations (`CombatantReferences.Adapt`) : une cible absente de la session (dans un autre secteur) est retirée à une forme à comportement ; une forme liée à une cible absente n'est pas simulée dans la session (le combat s'y arrête, sans nouvel essai sans fin ni place gardée) ; une première forme refusée à l'ouverture de la partie laisse le chef absent au lieu de faire échouer la partie. Les créatures d'événement (zones d'un seul secteur aujourd'hui) passent par la même règle (une créature liée à une cible absente ne vient pas). Les personnages entrent sans cible (pas concernés).
- **Victoire et butin** : la victoire n'est récompensée que si le personnage a joué ce tick **dans la session du chef** (celle du début du tick, ou de la session renouvelée suivie dès `AfterSector`) ; le butin d'une forme ne vient que d'un chef de la session du personnage. Les places gardées pour les formes à venir le sont dans la session du secteur du chef, pour les seuls combats qui ont une session.
- **Registre (tout ou rien), borne exacte** (relecture indépendante de la PR #159) : quand une session peut naître avant le tick des secteurs, la borne compte, pour chaque session terminée, les morts possibles de la suivante à la place des siennes (créatures de départ à l'heure du renouvellement, chefs qui y arrivent ou y sont emportés), et pour chaque secteur fermé qui s'ouvre avant le tick (joueur en attente, entrée annoncée), celles de sa session ; plus une clé par joueur qui arrive. Avant, toutes les créatures de l'aire (et tous les chefs) s'ajoutaient aux morts possibles des sessions terminées : un tick pouvait être refusé à tort près du plafond.
- **Parités** : les Vallons sans événement du monde jouent de même (journal octet par octet, trace, sauvegarde) en session de zone (le chemin d'avant) et sur l'hôte au cœur seul ; et de même sur l'hôte à deux secteurs tant que le personnage reste dans le cœur (trace, personnage sauvegardé ; un départ près du voisin l'ouvre, avec son rappel de naissance).
- **Limites** : un chef ne peut mourir sans le personnage dans sa session qu'abattu par un autre acteur (impossible en solo : aucune autre source de dégâts) ; une victoire au tick même d'un passage n'est pas constructible avec le contenu actuel (le passage demande d'être à plus de 16 m d'un chef, qui frappe au contact). ### Événements du monde et cicatrices liés à leur secteur (sous-lot V2.28b (2c), suite)

**Décision de Damien du 14 novembre 2026, 11 h 20 (« AAA », 3)** : chaque événement du monde est lié au **secteur de son lieu**, et le validateur vérifie que ses groupes y tiennent. Aucun format ne change (sauvegarde, zone, journal, moteur, règles) ; une règle du validateur de plus.

- **Lieu d'un événement** : la place de sa première variante (`groups[0].position`), sinon sa première créature (`WorldSession.PlaceOf`) ; son secteur est celui qui possède ce point (`SectorMap.OwnerOf`, `WorldEvents.SectorOf`). Les échos rôdeurs d'une cicatrice suivent l'événement qui l'a laissée.
- **Validateur** (zone à région) : places des variantes, créatures et échos rôdeurs de chaque variante dans le secteur du lieu (`$.data.events[i].groups[j].position`, `.creatures[k].position`, `.haunts[k].position`), à au moins 8 m de ses bords intérieurs. Une propagation de cicatrice passe d'une variante à l'autre du même événement : elle reste donc dans le secteur. Les événements des Vallons livrés sont tous dans le cœur.
- **Qui est tenu par l'hôte** : une zone à plusieurs secteurs avec des événements du monde l'est désormais. **Changement de comportement** : les Vallons livrés (cœur seul) **renouvellent leur session sans coupure** au bout d'une heure de jeu, comme une zone sans événement depuis le (2b) (avant, la partie reprenait au dernier point sûr) ; tant que la session dure, ils jouent octet pour octet comme avant.
- **Un événement a lieu au temps du monde, secteur ouvert ou non** (**décision de Damien du 14 novembre 2026, 17 h 18**, « AAA », 2 : même issue que si le joueur était absent) : départ, vagues, fin et issue suivent les ticks du monde (`Zone.WorldTick`), jamais ceux de la session (des sessions renouvelées toutes les 30 s donnent les mêmes instants qu'une session d'une heure). Ses créatures vivent dans la session du secteur de son lieu ; secteur fermé, elles attendent **sans place réservée** (`NeedsPlace`) et arrivent à l'ouverture, après une place réservée dans cette session.
- **Session renouvelée** (**décision de Damien du 14 novembre 2026, 17 h 18**, « AAA », 1) : les créatures d'événement présentes et vivantes continuent telles quelles dans la session nouvelle (place, PV, ressources emportés ; `WorldEvents.Renew`, appelé par le rappel de naissance de l'hôte avant toute mutation, en deux temps : arrivées sur le moteur neuf, puis adoption). L'état emporté est gardé jusqu'à l'**arrivée effective** lue sur le moteur (`ArrivedTick`) : une arrivée refusée réessaie avec lui ; une laisse l'efface.
- **Secteur fermé pendant l'événement, vraie réouverture** (revue Codex de la PR #160, 1er tour) : dès que l'hôte ne tient plus la session où jouait une créature (secteur fermé, ou fermé puis rouvert), elle est relevée sur cette session (morte : vaincue, blessée ou non par le personnage), puis, vivante, remise en attente sans place : l'occurrence avance au temps du monde, une créature absente s'en va à l'échéance, et l'événement finit avec son issue normale (faille restée ouverte : perdue, une cicatrice) sans bloquer les occurrences suivantes ; à une réouverture pendant l'événement, la créature revient à sa place, PV pleins, après une place réservée dans la session du moment. Les combats de chefs n'ont pas d'échéance : un secteur fermé les laisse en sommeil jusqu'à sa réouverture (aucun blocage) ; les populations sont tenues par l'hôte, secteur par secteur.
- **Places et registre** : les places réservées et pas encore prises comptent dans les places gardées **de leur secteur** (`WorldEvents.PendingIn`, `WorldSession.ReservedIn`), que reçoivent les populations de ce secteur ; la borne du registre d'un renouvellement compte les créatures d'événement emportées (`WorldEvents.JoinsAtBirth`) : tout ou rien, rien ne lève.
- **Une seule règle des morts qui inscrivent une clé** (revue Codex de la PR #160, 2e tour) : un combattant mortel et pas transitoire (`Zone.KeyedDeath`) ; le moteur de la session (morts possibles, inscription) et toutes les bornes du registre (combattants de départ d'une session qui naît, chefs et créatures d'événement emportés) passent par elle : un écho rôdeur emporté au renouvellement ne compte aucune clé (avant, une clé fictive par écho rendait le renouvellement impossible près du plafond alors qu'il tenait).
- **Fermer une faille** : seulement depuis la session du secteur de l'événement (sinon `TooFar`).
- **Parités** : les Vallons avec leurs événements jouent de même (journal octet par octet, trace, sauvegarde) en session de zone et sur l'hôte au cœur seul, et de même sur l'hôte à deux secteurs tant que le personnage reste dans le cœur (trace, personnage sauvegardé), juste avant l'attaque du hameau et la faille du Seuil.
- **Poursuite hors du secteur** (**décision de Damien du 14 novembre 2026, 17 h 18**, « AAA », 3) : une créature d'événement qui suit le personnage hors de son secteur le lâche au bout de la marge de 32 m, revient à sa place et reprend tous ses PV, comme un chef (essai dédié).
- **Relecture indépendante de la PR #160** : une créature morte au dernier tick de la session (que le pas des événements ne relit plus, la session étant finie) est relevée par le renouvellement avant tout remplacement : elle ne revient pas vivante et sa mort compte pour l'issue ; les identités de la session finie sont purgées ; aucune allocation par tick ajoutée (délégués gardés, boucles, décor rangé une fois par session pour la règle de place libre).
- **Limites** : la grande carte n'est pas encore livrée : les Vallons livrés tiennent dans le cœur, aucun passage n'y est encore possible (le chemin à plusieurs secteurs est essayé sur une zone d'essai et sur des Vallons agrandis).

### Règle d'arrivée à un point sûr (sous-lot V2.28b)

`WorldSession.SafeArrival` (fonction pure : même sauvegarde et mêmes données, même arrivée), la même pour **toute** session ouverte à un point sûr : jeu relancé, halte, reprise après une défaite ou une fin de session, voyage rapide, couvre-feu, entrée de la zone.

1. La place du point sûr si elle est libre au début de la session.
2. Sinon la place libre la plus proche par la règle d'arrivée des secteurs (`SectorWorld.NearestFree` : anneaux de 0,5 m jusqu'à 8 m, huit directions dans un ordre fixe ; dans l'aire, hors du décor et de toute emprise solide posée au début : créatures de départ, créatures qui arrivent au premier tick, premières formes des chefs).
3. Sans aucune place libre autour de lui : l'entrée de la zone, à sa place libre la plus proche. Le couvre-feu suit la règle entière (le joueur n'y choisit pas sa destination) : sans place libre autour du point sûr du couvre-feu, il est reconduit à l'entrée de la zone, et le message le dit. **Le voyage rapide, non** : **décision de Damien du 13 novembre 2026, 19 h 51** (« Non 2 pardon », rapportée par la session principale) : sans aucune place libre à 8 m de la destination, le voyage est **refusé** (`TravelRefusal.Blocked`, texte `text.ui.travel.blocked`) et le personnage ne bouge pas ; refus atomique : ni déplacement, ni temps, ni session, ni sauvegarde, ni voyage compté. `CanTravel` le dit d'avance (relecture indépendante de la PR #157) : l'écran du voyage grise le bouton avec la raison ; la règle d'arrivée y est calculée au plus une fois par destination et par tick.
4. Sans aucune place libre autour de l'entrée non plus : l'entrée même. L'arrivée y est refusée tant que la place est prise (`AdventureSession.Stranded`, message « Une créature occupe le point sûr ») et une reprise réessaie : c'est le seul cas où ce dernier recours d'avant le V2.28b sert encore.

Avant le V2.28b, seule la relance du jeu avait ce repli (V2.28a) ; une halte, une reprise ou un voyage sur un point sûr occupé arrivaient sur le point sûr même et réessayaient sans fin. Une porte reste une arrivée à la place de la porte. La halte et la reprise passent à la règle le point sûr que la session tient (`WorldSession.LastSafePoint`, toujours un point sûr de sa zone) : rien ne le remplace en silence par l'entrée. Pour les essais du dernier recours, la portée de la règle se règle de 0 à 16 anneaux (`SafeArrival(…, rings)`, `AdventureSession.Load(…, arrivalRings)`) ; le jeu prend 16 (`WorldSession.ArrivalRings`).

## Point de reprise (sous-lot V2.28a)

Première partie du sous-lot V2.28 ([plan](PLAN_GRANDE_CARTE.md#3-les-trois-étages-recommandation-sur-la-base-du-retenu), « reprise d'une partie ») : **sauvegarde en version 19** (18 et antérieures encore lues, mises à jour).

```json
"resume": { "safePoint": "place_du_bourg", "sector": "s07_06" }
```

| Champ | Bornes |
|---|---|
| `resume` | facultatif ; absent : la partie reprend à l'entrée de la zone (`data.zone`), comme avant |
| `safePoint` | obligatoire ; identifiant local d'un point sûr (minuscules, chiffres et « _ », une lettre d'abord, 64 caractères au plus : le format des zones) |
| `sector` | facultatif ; nom d'un secteur de simulation (« s07_06 ») ; absent pour une zone sans région (un intérieur) |

- **Sens** (retenu par Damien le 13 novembre 2026 : le dernier point sûr approché, même sans halte) : le dernier point sûr approché dans la zone de la sauvegarde (`WorldSession.LastSafePoint`) : celui où la session a commencé (entrée, halte, voyage rapide, couvre-feu ; arrivé par une porte : le point sûr non secret le plus proche d'elle, à égalité l'ordre ordinal des identifiants), puis le dernier dont le personnage, présent et vivant, s'est approché à **5 m** (`WorldSession.RestRange`, la distance de la halte et de la découverte ; jamais un point secret pas encore révélé).
- **Le point sûr fait foi** ; `sector` est le secteur qui simule sa place (`SectorMap.OwnerOf`), écrit pour que l'hôte des secteurs sache lequel ouvrir (suite du V2.28). Il est **recalculé des données** à chaque sauvegarde : un secteur périmé (point sûr déplacé par les données, comme la place du Bourg au V2.30.1) n'est pas une erreur, la partie reprend au point sûr là où il est maintenant.
- **Reprise** (`WorldSession.ResumeSafePoint`, fonction pure) : le point sûr de `resume` s'il est de la zone de la sauvegarde, s'il existe encore dans ses données et s'il n'est pas un point secret dont le personnage ne connaît pas le fait ; sinon **l'entrée de la zone**, sans erreur. Une zone que les données ne relient plus reprend à l'entrée de la zone de départ (le point de reprise n'est pas gardé).
- **Point sûr occupé** (relecture indépendante de la PR #155 ; règle étendue à toute session au V2.28b, [plus bas](#règle-darrivée-à-un-point-sûr-sous-lot-v228b)) : si une créature tient la place du point sûr au début de la session (une créature qui arrive au premier tick passe avant le personnage ; le validateur des zones ne refuse que les créatures de départ et les formes de chefs), le personnage arrive à la **place libre la plus proche** (anneaux de 0,5 m jusqu'à 8 m), sinon à **l'entrée de la zone**. Sans erreur ni attente : une sauvegarde ne reste jamais bloquée sur un point sûr occupé. Avec les données livrées le repli ne sert jamais (test : chaque point sûr libre à chaque heure du monde sur quatre jours).
- **Validation** (validateur unique, chemins précis) : `$.data.resume` (champ inconnu en version 18 et avant ; pas un objet), `$.data.resume.safePoint` (manquant, hors du format), `$.data.resume.sector` (mal nommé), champ inconnu refusé (`$.data.resume.position`). L'existence du point sûr n'est pas jugée par le validateur des sauvegardes (il ne connaît pas les zones) mais à la reprise, ci-dessus.
- **Écriture** : après `sectors`, avant `consumed` ; rien n'est écrit sans point de reprise (session sans zone du monde : celui de la sauvegarde d'entrée est rendu tel quel). Les copies d'une sauvegarde (voyage, porte, couvre-feu, outils d'essai des cicatrices et de l'heure) le gardent (`WorldSave.WithResume`).

### Eau des portes : marée et plongée (V2.50.1)

Schéma de zone 16 : `water` facultatif sur une porte (`DoorWater`). `tide: true` : la porte est **noyée à marée haute** seulement, à sec à marée basse ; sans `tide` : **toujours noyée**. `diveMs` : durée de la **plongée** quand elle est noyée, de 1 000 à 120 000 ms, multiple de 1 000 ; sans elle, une porte noyée ne se passe pas (un passage toujours noyé sans `diveMs` est refusé, `MissingField`). Les deux portes qui se répondent ont la **même eau** (`CheckDoors`, chemin `….water`). Un fichier de schéma 15 avec `water` est refusé ; sans elle, il reste lu.

Calculs purs (`EdS.World/Tides.cs`) : la **marée** vient de l'heure du monde (`WorldClock`, jamais d'horloge réelle), basse 3 h du monde puis haute 3 h (basse de 0 h à 3 h, de 6 h à 9 h, de 12 h à 15 h, de 18 h à 21 h : 22 min 30 s de jeu chacune) ; quand le **lac est gelé** (glace praticable à la date fournie, saisons), elle reste basse. Le **souffle** vaut 15 s, 30 s avec la coquille de souffle dans le sac. Une porte d'eau rend `Dry` (à pied), `Dive` (plongée : la plongée égale au souffle passe), `Drowned` (noyée sans plongée) ou `NoBreath` (plongée plus longue que le souffle) ; l'aventure (`AdventureSession.UseDoor`) refuse les deux derniers **avant toute sauvegarde**, sans rien changer (message, indication devant la porte), et annonce la plongée. Ni moteur, ni journal, ni sauvegarde ne changent : la marée se recalcule du tick du monde.
- **Pourquoi relever les bornes** : intérieurs du Bourg, bouches d'égout, entrées des dessous et niveaux de la mine, failles (§ 3 du plan). Les bornes sont celles des données ; le moteur n'en dépend pas (une session ne tient qu'une zone).

## Altérations (sous-lot 7.2)

`data.statuses` est une liste **ordonnée** de définitions (au plus 64) : l'ordre fixe la priorité des motifs de refus (la première altération bloquante l'emporte) et entre dans l'empreinte. Champs obligatoires : `id`, `category` (`dot`, `control`, `modifier`, `immunity` ; `buff` et `shield` depuis le sous-lot 8.2, voir ci-dessous), `durationMs`, `stacking` (`refresh`, `perSourceKeepStronger`, `keepLonger`, `ignore`), `resistance` (`none`, `defense`, `duration`). Champs facultatifs, à valeur neutre s'ils sont absents : `periodMs` et `damageType` (DOT), `blocks` (`skills`, `guard`, `parry`, `regeneration`, `assailantAttacks` ; `movement` depuis le sous-lot 11.4a), `interrupts` (`guard`, `parry`), `blockReason`, `damageTakenIncrease` (0 à 10), `movementSpeedModifier` (−1 à 1), `grantsOnExpiry`, `immuneTo`, `triggers` (lot 7.3), `modifiers` (sous-lot 8.2, renforcements seulement).

```json
{ "id": "stun", "category": "control", "durationMs": 1500, "stacking": "ignore", "resistance": "duration",
  "blocks": ["skills", "guard", "parry", "assailantAttacks", "movement"], "interrupts": ["guard", "parry"],
  "blockReason": "stunned", "grantsOnExpiry": "stunImmunity" }
```

Correctif 7.2 (contenu `0.4.1-provisoire`) : l'étourdissement passe de `keepLonger` à `ignore` ; un étourdissement actif refuse toute nouvelle application, ce qui garantit son expiration et l'immunité qui la suit.

Cohérence vérifiée par `StatusCatalog.Validate` (seule validation de gameplay), erreurs rattachées à `$.data.statuses[i].champ` : identifiants uniques ; durée positive, multiple du tick, au plus 24 h ; un DOT a une période multiple du tick qui divise sa durée, un type de dégâts, le cumul par source et la résistance `none` ou `defense`, et lui seul a période, type de dégâts, cumul par source ou résistance `defense` ; seul un contrôle a la résistance `duration` ; une altération qui bloque a un `blockReason` (et réciproquement) ; seule une immunité a `immuneTo`, qui désigne au moins une altération existante, sans doublon ni immunité ; un état accordé existe, n'est ni un DOT ni l'altération elle-même et n'accorde rien à son tour (profondeur 1). `combat.guard.breakStatus` désigne une altération existante, ni DOT ni immunité.

Applications (`applies`, dans le bloc `combat` d'une compétence et dans chaque attaque d'assaillant ; obligatoire, éventuellement vide) : `{"status": "bleed", "coefficient": 0.5}`. Sous-lot 8.3 : `target` facultatif (`self`, `allAllies`, `allEnemies`, relatifs à l'acteur) — l'application est alors faite une fois, après les impacts, à ces cibles, au lieu de chaque cible de l'action. Le coefficient est obligatoire pour un DOT et pour un bouclier (sous-lot 8.2 : fraction des PV max de la source), interdit sinon, dans [0, 100] ; une altération citée deux fois, inconnue, une immunité ou l'altération de rupture sont refusées. `stats.statusResistanceConstant` (K, 1000) est dans ]0, 10⁹] ; `statusResistance` d'un mannequin ou d'un assaillant (facultatif, 0 par défaut) dans [0, 10⁹].

## Déclencheurs (sous-lot 7.3)

Un déclencheur est une donnée, jamais du code : `triggers` est une liste facultative (au plus 8) sur un **talent** ou une **compétence** de classe (passive, active ou ultime ; seuls les talents de rang ≥ 1 et les compétences équipées sont actifs), sur une **altération** du catalogue (`statuses[].triggers`, actif tant que l'instance existe) et sur un **assaillant** de scénario (Q4, pour les tests et les entraînements). L'équipement est réservé (Q9), non implémenté. Depuis le sous-lot 8.5, des talents et un passif du Bastion livré en portent (voir « Bastion (sous-lot 8.5) ») ; jusque-là, aucune donnée livrée n'en portait (Q14).

```json
{ "on": "onBlock", "role": "source", "cooldownMs": 500, "filter": { "damageType": "physique" },
  "effects": [ { "type": "strike", "target": "eventTarget", "coefficient": 1, "powerType": "physique", "damageType": "magique", "unblockable": true },
               { "type": "applyStatus", "target": "eventTarget", "status": "bleed", "coefficient": { "base": 0.25, "perRank": 0.05 } } ] }
```

- `on` (obligatoire) : `onSkillCast`, `onHitDealt`, `onHitTaken`, `onBlock`, `onPerfectParry`, `onGuardBroken`, `onResourceGained`, `onStateApplied`, `onStateExpired`, `onStateRemoved`, `onDotTick`, `onDeath` (événements observables de §1.2 seulement ; aucun diagnostic n'est observable).
- `role` : `self`, `source` ou `target`, obligatoire quand le type en admet plusieurs (blocage, parade, rupture, états, DOT), interdit sinon ; `onDeath` n'admet que `source` (le tueur), `onHitTaken` que `target`.
- `filter` (facultatif) : `skills` (identifiants de compétences ou d'attaques d'assaillant), `damageType`, `defense` (liste parmi `none`, `guard`, `parry`, `unblockable`, `guardBroken`), `status` ou `category` (pas les deux), `resource` (`rampartCharges` ou `resonance`), `renewed` ; chaque critère doit avoir un sens pour `on`. Le filtre ne lit que l'instantané de l'événement.
- `cooldownMs` : recharge interne dans [0, 24 h], multiple du tick.
- `effects` : 1 à 4, exécutés dans l'ordre comme une seule réaction. `strike` : `target` (`eventSource`, `eventTarget`, `allEnemies`, jamais le porteur), `coefficient` (0 à 100), `powerType`, `damageType`, `unblockable` facultatif. `applyStatus` : `target` (les mêmes, ou `bearer`), `status` (mêmes règles que `applies` : coefficient obligatoire pour un DOT, ni immunité ni rupture de garde). `gainResource` : `resource` (`resonance`, `rampartCharges`, `endurance`), `amount` entier (au plus le coût maximal d'une compétence), toujours au porteur. `onDeath` ne vise pas `eventTarget` (le mort).
- Valeurs par rang : un nombre, ou `{ "base": x, "perRank": y }` pour un talent à plusieurs rangs seulement, borné à chaque rang possible. Décision du 18/10/2026 : un perRank non nul sur un talent à un seul rang est refusé (il serait sans effet), comme pour les modificateurs.

Validation unique (`TriggerDefinition.ValidateList` et `ValidateReferences`, appelées par les lecteurs de règles, de classes et de scénarios et par `CombatSetup.Validate`), erreurs localisées à `…triggers[i].champ`. Un **cycle statique** possible (un déclencheur dont les effets peuvent produire l'événement qu'il observe, directement ou par une chaîne de déclencheurs) est un **avertissement** du rapport, jamais une erreur (Q1) : la règle de cycle et la profondeur garantissent la terminaison. `combat.limits.maxTriggerDepth` (4, de 0 à 8) borne la profondeur. Comportement au combat : [MOTEUR.md](MOTEUR.md#déclencheurs-sous-lot-73).

### Renforcements et boucliers (sous-lot 8.2)

Deux catégories s'ajoutent au catalogue (schéma de règles 7, puis 8 au sous-lot 8.3 ; un fichier antérieur est refusé sans migration), sans aucune définition livrée au sous-lot 8.2 (le bouclier et les renforcements du Bastion le sont au sous-lot 8.4, voir plus bas).

- **Renforcement** (`category: "buff"`) : porte `modifiers`, liste obligatoire (1 à 8) de modificateurs actifs tant que l'instance existe sur son porteur. Clés admises : `damageDealt` (catégorie de bonus « altération », comme la Fragilité), `damageTaken` (réduction, valeur négative, sous le plafond total `combat.damageTaken.maxReduction`), `guard.upkeepPerSecond` et, depuis le sous-lot 8.4 (schéma de règles 9), `guard.noUpkeep` (drapeau, `add` = 1 : garde sans entretien tant que le renforcement dure). Chaque élément a `key` et `add` (un nombre, ou `{ "base": x }` : `perRank` non nul refusé, une altération n'a pas de rang), sans `conditions` (refusées : le modificateur vaut tant que le renforcement est actif). Mêmes contrôles de bornes, de doublon et de valeur nulle que pour un passif. Cumul : `refresh`, `keepLonger` ou `ignore` (le cumul par source est refusé : une instance au plus par définition et par porteur).
- **Bouclier** (`category: "shield"`) : cumul `perSourceKeepStronger` obligatoire (un bouclier par source, renouvelé à la plus forte valeur), résistance `none`, sans `modifiers`. Sa valeur est fixée à l'application : ⌊ PV max de la source × coefficient × (1 + `shield.potencyDealt` de la source) ⌋. Le coefficient d'application est donc obligatoire (`applies[].coefficient` ou `coefficient` d'un effet `applyStatus` de déclencheur) ; une source sans PV max (mannequin, assaillant) pose un bouclier vide, refusé au combat (`stateBlocked`, `empty`). Un bouclier ne peut pas être accordé à l'expiration d'une autre altération (`grantsOnExpiry`) : aucune application ne fixerait sa valeur.
- Les autres catégories n'ont pas de `modifiers` (une liste vide équivaut à une liste absente).

```json
{ "id": "fortifie", "category": "buff", "durationMs": 8000, "stacking": "refresh", "resistance": "none",
  "modifiers": [ { "key": "damageTaken", "add": -0.3 } ] },
{ "id": "egide", "category": "shield", "durationMs": 4000, "stacking": "perSourceKeepStronger", "resistance": "none" }
```

Erreurs rattachées à `$.data.statuses[i].modifiers` (renforcement sans modificateur, modificateurs hors renforcement), `…modifiers[k].key` (clé inconnue ou non admise, doublon), `…modifiers[k].add` (bornes, `perRank`, valeur nulle, `damageTaken` positif), `…modifiers[k].conditions` et `$.data.statuses[i].stacking` (bouclier sans cumul par source, renforcement avec). Forme canonique : après les déclencheurs de l'altération, `modifiers.count` puis chaque modificateur comme pour une classe ; rien sans modificateur. Le schéma JSON (`rules.schema.json`) reprend les clés admises et l'absence de conditions ; `Lot82StatusDataTests` vérifie qu'il décrit exactement les champs lus, les catégories du domaine et les clés admises.

### Provocations et protections (sous-lot 8.3)

Deux catégories de plus (schéma de règles 8), aucune livrée au sous-lot 8.3 (provocations du Bastion livrées au sous-lot 8.4) : `taunt` (provocation d'un assaillant) et `protection` (transfert d'une part des dégâts d'un allié à son protecteur). Toutes deux se cumulent par source (`perSourceKeepStronger` obligatoire), ne sont jamais accordées à l'expiration d'une autre altération (elles dépendent d'une source vivante) et sont retirées à la mort de leur source. Une provocation a la résistance `none` ou `duration` (sa durée se réduit comme celle d'un contrôle). Une protection exige `redirectRatio` dans ]0, 1] (part des dégâts transférée ; champ refusé sur toute autre catégorie) et a la résistance `none`.

```json
{ "id": "provocation", "category": "taunt", "durationMs": 3000, "stacking": "perSourceKeepStronger", "resistance": "none" },
{ "id": "lienProtecteur", "category": "protection", "durationMs": 6000, "stacking": "perSourceKeepStronger", "resistance": "none", "redirectRatio": 0.25 }
```

Forme canonique : `redirectRatio` écrit pour chaque altération (0 hors protection), après ses modificateurs. Comportement au combat : [MOTEUR.md](MOTEUR.md#provocation-protection-et-rôle-allié-sous-lot-83).

## Builds de référence (sous-lot 8.5)

Un fichier par classe (`data/v0/builds/<classe>.json`, `kind: "builds"`, schéma 1, `data/schemas/builds.schema.json`), même en-tête que les autres fichiers de données. Décision A12 : les builds de comparaison sont des données, pas du code de test.

```json
{
  "schemaVersion": 1, "kind": "builds", "contentVersion": "0.1.0-provisoire",
  "data": { "class": "class.bastion", "builds": [
    { "id": "build.bastion.rempart", "name": "Rempart", "category": "reference",
      "build": { "level": 30, "attributes": { "force": 30, "dexterite": 10, "intelligence": 6, "vitalite": 30, "volonte": 15, "endurance": 20 },
                 "talents": { "talent.bastion.rempart.garde_stable": 3, … }, "activeSkills": [ … ], "ultimate": "skill.bastion.bastion_absolu",
                 "passiveSkills": [ … ] } } ] }
}
```

- `class` (obligatoire) : une classe chargée du même dossier.
- `builds` (obligatoire) : 1 à 64 builds ; chacun a `id` (identifiant stable `build.<classe>.<nom>`, de la classe du fichier, unique dans toutes les données), `name` (non vide), `category` (`reference` : build de spécialisation comparé ; `control` : build de contrôle) et `build`, de la même forme que le build d'un personnage de scénario (contrôle de forme partagé, `BuildShape`).
- Validation : `BuildSetJsonReader` (forme) → `BuildSetDocument` → `BuildSetValidator` (en-tête, présence, identifiants, catégories, forme du build) → `BuildValidator` (règles du build, contre la classe et la progression des règles). Une violation du build est rattachée au champ fautif d'après l'élément qu'elle désigne (revue Codex de la PR #9) : `$.data.builds[i].build.talents.<id>` pour un talent (inconnu, rang, prérequis, seuil du majeur), `.talents` pour le total des points ou des majeurs, `.activeSkills[n]`, `.passiveSkills[n]` ou `.ultimate` pour un emplacement, `.activeSkills` ou `.passiveSkills` pour leur nombre, `.level`, `.attributes.<attribut>` ; le code du validateur est dans le message (`UnknownReference` pour un talent ou une compétence inconnus, `InvalidValue` sinon). Dans un scénario, une violation du build reste rattachée à `combatants[i].build` (`CombatSetup.Validate`), comme depuis le lot 5.
- Chargement : `GameDataLoader.Load` lit `builds/*.json` après les classes (ordre des noms de fichiers) ; un fichier refusé, ou un identifiant déjà défini par un autre fichier (`DuplicateId`), fait échouer le chargement comme une classe refusée. `GameData.BuildSets` et `GameData.TryGetBuild` les exposent. Les builds n'entrent **pas** dans l'identité des données d'un combat : un scénario recopie le build de chaque personnage, et le journal reste inchangé.
- Pas d'empreinte pour ce fichier : il n'est lu par aucun combat (une référence aux builds depuis un scénario pourra venir avec les scénarios S1 à S5, sous-lot 8.6).

Contenu livré et choix des points : [BUILDS.md](BUILDS.md#builds-de-référence-sous-lot-85-datav0buildsbastionjson).

## Scénarios de mesure et rapport (sous-lot 8.6)

Les scénarios de mesure sont des scénarios ordinaires (`kind: "scenario"`, schéma 3, puis 4 depuis le sous-lot 11.1) rangés dans `scenarios/mesures` et nommés `s<n>_<nom>.json` (identifiant « S<n> ») ; un autre nom est ignoré par `eds report`, et deux fichiers au même numéro (`s1_a.json`, `s1_b.json`) sont refusés. Chacun a un personnage `bastion` (son build du fichier n'est qu'une valeur par défaut, celui du Rempart, remplacée à chaque mesure) et aucune commande (le pilote les ajoute). Contenu : [BUILDS.md](BUILDS.md#mesures-des-builds-sous-lot-86). Aucun format de scénario n'est ajouté : un scénario ne référence toujours pas un build par son identifiant.

```bash
dotnet run --project src/EdS.Cli -- report                                   # S1 à S5 × 5 builds × 3 profils, texte
dotnet run --project src/EdS.Cli -- report --profile standard --build build.bastion.rempart --build build.bastion.contrecoup
dotnet run --project src/EdS.Cli -- report --json > rapport.json            # rapport JSON reproductible octet par octet
dotnet run --project src/EdS.Cli -- report --logs journaux --strict          # journaux rejouables ; code 3 si un objectif échoue
```

Options : dossier (défaut `scenarios/mesures`), `--data` (défaut `data/v0`), `--build` et `--profile` répétables (défaut : tous les builds de la classe du personnage `bastion`, dans l'ordre du fichier ; `beginner`, `standard`, `expert`), `--json`, `--logs <dossier>` (journal de chaque combat, `<scénario>__<build>__<profil>.jsonl`, rejouable avec `eds replay`), `--strict`. Rapport texte aux fins de ligne `\n` sur toutes les plateformes. Codes de sortie : 0, 1 (usage, données ou scénario refusés, numéro de scénario en double), 2 (un combat interrompu par une limite du moteur : mesures de diagnostic), 3 (avec `--strict`, au moins un objectif non atteint).

Rapport JSON (`kind: "measureReport"`, `formatVersion` 1) : `engineVersion`, `data` (contenu et empreinte des règles, de chaque classe), `objectiveProfile`, `scenarios` (`id`, `name`, `durationMs`, `seed`), `builds`, `results` (par combat : `scenario`, `build`, `profile`, `durationMs`, `aborted`, `end`, `damageDealt`, `dps`, `healthLost`, `maxHealth`, `avoided`, `mitigated`, `absorbed`, `transferred`, `redirected`, `died`, `survivalSeconds`, `allyDied` et `allySurvivalSeconds` — `null` sans allié —, `blocks`, `perfectParries`, `guardBreaks`, `skillsCast`, `ultimates`, `commandsRejected`, `peaksPercent` `work`, `events`, `queue`) et `objectives` (`id`, `description`, `passed` — `null` si non mesuré —, `detail`). Propriétés dans un ordre fixe, nombres décimaux invariants, fin de ligne finale.

## Modificateurs (sous-lot 8.1)

Un modificateur change une règle de combat ou une statistique **du porteur** : `modifiers` est une liste facultative (au plus 8) sur un **talent** (actif dès le rang 1, valeur au rang du build) ou une **compétence passive** équipée (rang 1, sans `perRank`). Une compétence active ou ultime n'en porte pas (refus). Au plus 512 modificateurs par classe, vérifiés avec les autres plafonds globaux. Depuis le sous-lot 8.5, les talents et passifs du Bastion livré en portent (« Bastion (sous-lot 8.5) »).

```json
"modifiers": [
  { "key": "guard.damageReduction", "add": { "base": 0.02, "perRank": 0.02 } },
  { "key": "damageTaken", "add": -0.02, "conditions": ["whileGuarding", "perRampartCharge"] },
  { "key": "skill.bastion.frappe_du_rempart.cooldownMs", "add": -500 }
]
```

- `key` (obligatoire), liste fermée :

| Clé | Nature | Valeur déclarée (rang 1 et rang max) | Valeur résultante |
|---|---|---|---|
| `guard.damageReduction` | fraction | ±1 (classe) ; ±plafond des règles (0,75), vérifié au combat | [0 ; `combat.guard.maxDamageReduction`] |
| `guard.upkeepPerSecond` | décimal par seconde | ±10⁶ | [0 ; 2³¹ − 1] |
| `guard.costPerBlock` | entier | ±10⁶ | [0 ; 2³¹ − 1] |
| `guard.noUpkeepBreak` | drapeau, `add` = 1 exactement | — | — |
| `guard.reductionAtZeroEndurance` | fraction | ±1 (classe) ; ±plafond des règles (0,75), vérifié au combat | [0 ; réduction de garde effective] |
| `guard.breakShortenPerCharge` | ms | ±86 400 000 | [0 ; 24 h] |
| `parry.windowMs` | ms | ±500 | [1 tick ; ⌊500 / tick⌋ × tick] |
| `parry.failureRecoveryMs` | ms | ±86 400 000 | [0 ; 24 h] |
| `rampartCharges.max` | entier | ±10 | [0 ; 10] |
| `resonance.perDirectHit` | entier | ±10⁶ | [0 ; 2³¹ − 1] |
| `endurance.max` | entier, plat | ±10⁶ | ≥ 0 |
| `endurance.regenPerSecond` | décimal par seconde | ±10⁶ | [0 ; 2³¹ − 1] |
| `maxHealth` | fraction du PV max calculé | ±10 | pourcentage résultant [−0,9 ; 10] |
| `statusResistance` | décimal, plat | ±10⁶ | ≥ 0 |
| `damageDealt` | fraction, conditionnelle | ±10 | catégorie de bonus « talent » |
| `damageTaken` | fraction ≤ 0, conditionnelle | [−1 ; 0] | [−1 ; 0] |
| `status.<id>.durationDealt` | ms | ±86 400 000 | durée [1 tick ; 24 h] |
| `status.<id>.durationTaken` | ms | ±86 400 000 | durée [1 tick ; 24 h] |
| `<id de compétence>.coefficient` | fraction | ±100 | [0 ; 100] |
| `<id de compétence>.cooldownMs` | ms | ±86 400 000 | [0 ; 24 h] |
| `shield.potencyDealt` | fraction (sous-lot 8.2) | ±10 | ≥ −1 en effet : facteur (1 + puissance) ramené à 0 au plus bas |
| `protection.redirectRatio` | fraction (sous-lot 8.3) | ±1 | somme dans [−1, 1] ; part effective d'une protection posée (définition + somme) dans [0, 1] |
| `protection.redirectThroughGuard` | drapeau, `add` = 1 exactement (sous-lot 8.3) | — | les dégâts transférés au porteur passent par sa garde (réduction seulement) quand il garde |
| `guard.noUpkeep` | drapeau, `add` = 1 exactement (sous-lot 8.4) | — | garde sans entretien : coût par seconde effectif nul (permanent, ou tant qu'un renforcement qui le porte est actif) |

  `<id>` est un identifiant d'altération du catalogue (`status.stun.durationTaken`) ; une clé de compétence est l'identifiant complet d'une compétence de la classe qui se lance (bloc `combat`), suivi du suffixe (`skill.bastion.frappe_du_rempart.coefficient`). `durationDealt` est refusé pour une immunité ou l'altération de rupture de garde (jamais appliquées directement).
- `add` (obligatoire) : un nombre, ou `{ "base": x, "perRank": y }` pour un talent à plusieurs rangs (valeur au rang r : base + (r − 1) × perRank), bornée au rang 1 et au rang maximal. Une valeur nulle à chaque rang (sans effet) est refusée, comme un perRank non nul sur un talent à un seul rang. Entiers et ms : base et perRank entiers ; ms : multiples du tick (et de la période pour une altération à dégâts périodiques), vérifiés au combat. Pour une règle à plafond absolu, la borne d'une valeur déclarée est la largeur de ce plafond : un modificateur seul qui le dépasse est une erreur de données ; seules les combinaisons de plusieurs sources sont **écrêtées** (jamais refusées).
- `conditions` (facultatif, X2), seulement sur `damageDealt` et `damageTaken` : `whileGuarding` (porteur en garde), `perRampartCharge` (× Charges détenues), `perResonanceStep` (× ⌊Résonance / 10⌋) ; combinables, mais au plus une condition multiplicative (`perRampartCharge` et `perResonanceStep` ensemble refusés). Liste vide = absente.
- Une même clé avec le même ensemble de conditions deux fois chez un même porteur : `DuplicateId`. La même clé sur plusieurs porteurs s'additionne.

Validation : forme (`ModifierShape`, lecteur JSON), puis `ModifierDefinition.ValidateList` dans `ClassDefinition.Validate` (clés, conditions, doublons, bornes, entiers, drapeau, compétence référencée), puis `ModifierDefinition.ValidateReferences` dans `CombatSetup.Validate` (altération du catalogue, multiples du tick et de la période). Au plus une erreur par valeur. Erreurs de la classe localisées à `…modifiers` (porteur non admis, plus de 8 modificateurs), `…modifiers[i]` (élément qui n'est pas un objet), `…modifiers[i].<champ>` (champ inconnu), `…modifiers[i].key`, `.add`, `.add.base`, `.add.perRank` ou `.add.<champ>` (forme de la valeur : champ absent, de type faux ou inconnu), `.conditions` ou `.conditions[k]` (condition inconnue, répétée ou de type faux), et à `skills` pour le plafond de 512 par classe ; au combat, les erreurs de références sont rattachées à `combatants[i].class`, chemin interne dans le message, comme pour les déclencheurs (voir [MOTEUR.md](MOTEUR.md#modificateurs-sous-lot-81)). Forme canonique : après les déclencheurs du talent ou de la compétence, `modifiers.count`, puis pour chacun `key`, `add` (`base` ou `base+perRank/rank`) et la liste `conditions`, écrite dans l'ordre fixe `whileGuarding`, `perRampartCharge`, `perResonanceStep` quel que soit l'ordre déclaré (un ensemble : même empreinte) ; l'ordre des modificateurs, lui, fait partie du contenu. Une liste vide n'écrit rien (même empreinte qu'une liste absente). Le schéma JSON reprend les règles exprimables sans les règles du jeu (passive seulement et sans perRank, conditions de `damageDealt` et `damageTaken`, une seule multiplicative, drapeau à 1, `damageTaken` négatif, jamais nul) et n'est jamais plus strict que le programme : `Lot81SchemaConformanceTests` le vérifie sur plus de 13 000 fichiers dérivés de bastion.json (chaque clé, valeur, porteur dont le talent majeur, ensemble de conditions et liste type). Comportement au combat : [MOTEUR.md](MOTEUR.md#modificateurs-sous-lot-81).

## Corruption qui s'étend et recule (sous-lot V2.42.1)

Plan de la grande carte, § 7 (V2.42) : la corruption du Seuil gagne les terres autour du cercle des pierres levées ; le joueur la fait reculer en purifiant des autels. **Calculée, pas simulée** : où en est la corruption se recalcule du jour du monde et des autels purifiés (`CorruptionRules`, fonctions pures, `EdS.World/Corruption.cs`) ; la sauvegarde ne garde que le jour de la dernière purification de chaque autel (v32, `character.corruption`).

- **Décisions de Damien du 21 novembre 2026** : vitesse (une terre tous les 2 jours, un palier tous les 2 jours jusqu'au 3), créatures plus fortes de 10 % par palier, purification (150 points, 4 jours de répit), recul des terres que seule la terre purifiée nourrissait, et **purification de la source par un gros défi qui donne un répit à toute la région : décidée, à faire au sous-lot V2.42.3**.
- **Extension** : la source (le cercle des pierres levées) est corrompue depuis le jour 0, au palier maximal ; une terre est gagnée `spreadDays` (**2**) jours après la plus tôt corrompue de ses terres d'origine (`from`), puis prend un palier tous les `growDays` (**2**) jours jusqu'à `maxStage` (**3**). **Une seule terre de plus tous les 2 jours** (décision de Damien, revue de la PR #242) : la n-ième terre du fichier n'est jamais gagnée avant le jour n × `spreadDays` ; sans purification, les huit terres tombent l'une après l'autre, aux jours 2, 4, … 16, dans l'ordre du fichier. Un seul passage dans l'ordre du fichier (chaque terre après ses origines : jamais de boucle).
- **Purification** (`WorldSession.PurifyAltar`, touche d'action à l'autel, à 3 m du bord de l'emprise du personnage ; l'indication à l'écran suit la même portée) : la terre doit être corrompue aujourd'hui ; un **éclat de Seuil** est pris, **150 points** d'expérience donnés (sous le plafond), le fait `fact.corruption.autel_purifie` appris tout de suite, le jour gardé ; la terre est propre pendant `respiteDays` (**4**) jours, puis la corruption peut revenir. Refus atomiques : `NoArea` (terre inconnue, la source, ou pas de corruption dans cette zone), `TooFar`, `NotCorrupted` (rien à purifier, l'autel est encore dans son répit), `NoItem`, `Defeated`.
- **Corruption tenue par la source** (décision de Damien du 21 novembre 2026) : une terre coupée de toutes ses origines par des autels purifiés recule elle aussi (annoncée « reculée »), et revient `spreadDays` jours après que le froid a rejoint son origine. Une terre à deux origines garde la plus tôt (les confins du sud, nourris par les failles du sud et de l'est).
- **Créatures plus fortes** (décision de Damien du 21 novembre 2026) : dans une terre corrompue, les créatures ont **+10 % de PV et de dégâts bruts par palier** (`strengthPercent`, 110 % au palier 1, 130 % au palier 3 et à la source ; `ZoneScaling.Strengthen`, mêmes arrondis et plafonds que le réglage par niveau). Calcul vérifié (`CorruptionRules.StrengthAt` : la terre la plus corrompue qui contient la place de la créature, bord du disque compris) ; appliqué à la zone quand une partie s'ouvre (`CorruptionRules.Strengthen`, `ZoneDefinition.Strengthened` : combattants du scénario et modèles de leurs populations, ni chefs ni formes de chef ; jour du monde de la sauvegarde). Le moteur ne change pas.
- **Annonces** (`WorldSession.CorruptionNotices`, à chaque tick, pas au premier tick d'une session) : terre gagnée, plus forte, affaiblie ou reculée, autel purifié (avec l'expérience). Textes `text.corruption.*` et `text.ui.corruption.*` (textes 0.47.0).
- **Contenu** (corruption 0.1.0) : huit terres autour des pierres, gagnées dans cet ordre (jours 2 à 16) : le versant ouest des pierres, les failles du nord, de l'est et du sud, les landes du Seuil, les marches de l'abbaye, les confins du sud, la plaine de l'est ; chaque autel à plus de 8 m de toute route. Les autels ne sont pas des obstacles (scénario inchangé).
- **Affichage** (`EdS.Runtime`, `AdventureSession.Corruption`, `AltarInReach`, `PurifyAltar`, `CorruptionFadeAt`, `CorruptionLabel`) : marque en millièmes (palier sur maximal fois `1 − d²/r²`, la plus forte compte) pour les couleurs fanées ; Unity au sous-lot V2.42.2.
- **Unity (sous-lot V2.42.2)** : `CorruptionLooks` (`EdS.Runtime`, déterministe) pose dans chaque terre corrompue **12 pièces par palier** (arbres morts, souches, rochers fendus, cristaux sombres ; mêmes places d'un palier à l'autre, tirées de l'identifiant de la terre par `Pcg32`, à 6 m au moins de l'autel) et son autel, **corrompu** tant que la terre l'est, **purifié** sinon ; la source n'a que des cristaux et des rochers (ses autels sont ceux du cercle). `CorruptionDecorView` (Unity) construit les terres dont le bord est à moins de 250 m de la caméra, et reconstruit une terre quand son palier change. Les **8 modèles Tripo** (240 crédits au plus, validés par Damien le 21 novembre 2026 ; finition `finir_corruption.py` de l'atelier : un seul maillage, hauteur de la fiche, pivot au sol au centre, allégé à 50 %, textures de 1 024 px) (`arbre_corrompu_1`, `arbre_corrompu_2`, `souche_corrompue`, `rocher_corrompu_1`, `rocher_corrompu_2`, `cristaux_sombres`, `autel_corrompu`, `autel_purifie`) sont branchés par leur nom (`Assets/EdS/Modeles/Corruption/<nom>/<nom>.fbx`, menu du style, `StyleCatalog.CorruptionModel`). Les formes de remplacement de la même taille restent en repli pour un modèle absent (bois calciné, pierre grise, éclats violets ; autel purifié pâle et lumineux). Les couleurs se fanent dans une terre corrompue comme près d'une cicatrice (la plus forte des deux marques compte). On voit « F : purifier l'autel » à portée, et le libellé de la terre en haut de l'écran.
- **Tests** : `V242CorruptionTests`, `V2422CorruptionUnityTests` (catégorie World).
- **Limites** : les autels purifiés sont ceux du personnage (en solo, une sauvegarde ; pas encore partagés sur le serveur) ; la force des créatures est celle du début de la partie (une terre gagnée ou purifiée en cours de partie compte à la partie suivante) ; la source ne se purifie pas encore (V2.42.3) ; les terres sont des disques donnés par les données (pas calculées du relief) ; aucune créature de plus dans une terre corrompue.
- **Défi de la source (sous-lot V2.42.3, décision de Damien du 21 novembre 2026 : « un gros défi, difficile, qui donne un répit à toute la région »)** : `corruption.json` **version 2** (la 1, sans défi, encore lue), bloc `challenge` facultatif : `boss` (le **gardien de la source**, au format des chefs d'une zone : `id`, `scenario`, `forms`, `fact`, `rewards`, `loot` facultatif ; mêmes règles, `ZoneValidator.CheckBoss`, toutes ses formes dans le disque de la source et, zone à région, dans le secteur de la première ; la place des combattants est comptée sur la session du secteur du cercle), `minAltars` (0 au nombre de terres), `respiteDays` (1 à 30), `xp` (0 à 100 000) ; avec un défi, au plus 31 terres. Livré : trois formes (`scenarios/zones/vallons_gardien_source.json` : 1 000, 800 et 600 PV, poing, ruée, onde du Seuil à partir de la deuxième), 3 autels en répit, **8 jours** de répit, 400 points par victoire, 3 éclats de Seuil et le fait `fact.corruption.source_purifiee` à la première. **Monde** (`WorldSession.ChallengeSource`, refus atomiques `SourceChallengeRefusal` : pas de défi, personnage tombé, hors du disque de la source ou d'une autre session de secteur, défi en cours, région au repos, autels en répit trop peu nombreux, sauvegarde pleine, arrivée refusée par le moteur, registre du monde sans la place des morts possibles de toutes les formes du gardien (`RegistryFull`, revue Codex de la PR #252, 3e tour : cette place est ensuite réservée tant que le défi dure, `DeathReserve`), session sans les capacités de toutes les formes (`Capacity`, 4e tour : identités jamais rendues pour les trois formes en plus des réservées et de la réserve des quêtes, une place libre en plus des réservées, combat complété de leurs trois arrivées valide : identités de la session, majorant de file avec déclencheurs, précontrôle numérique, `BossFight.WhyNotAll`)) : la première forme arrive dans la session du personnage (`BossFight.StartAnew`, identité libre) ; le combat suit les règles des chefs (formes successives, récompense de la première victoire au registre, clé `zone.vallons/boss/gardien_de_la_source`). Gardien vaincu, personnage debout : la source est purifiée (jour gardé sous l'identifiant de la source dans `character.corruption`, **sauvegarde v33**), `xp` donnée, annonce `SourcePurified` (une seule pour toute la région). Toute la région recule : la source est propre jusqu'au jour + `respiteDays` (`CorruptionRules.SourceSince`), puis la corruption repart du cercle, une terre tous les 2 jours comme au début ; les créatures du cercle ne sont pas renforcées pendant ce répit. Personnage tombé, parti à plus de 30 m du disque (`SourceLeash`) ou sorti de la session : défi perdu (`ChallengeFailed`), la forme en jeu s'en va, rien ne change (revue Codex de la PR #252 : un départ refusé par le moteur ne bloque pas le réglement ; une forme suivante déjà programmée part dès son arrivée, même après un nouvel échec ; une forme refusée par le moteur 5 fois d'affilée, une par seconde, `SourceArrivalTries`, fait perdre le défi au lieu de réessayer sans fin). Rejouable après le répit (sans seconde récompense). **Unity** : touche F au cercle (`AdventureSession.SourceInReach`, `ChallengeSource`), indice `SourceHint` (autels en répit sur 3, ou jours de répit qui restent), le gardien prend le personnage du Gardien (dossier Mixamo `gardien`), textes de phase et de victoire propres. Formats inchangés : sauvegarde v33, `corruption.json` v2. **Décisions de Damien du 22 novembre 2026 (décidé)** : conditions de lancement : 3 autels encore dans leur répit ; répit régional de 8 jours ; 400 points par victoire, plus 3 éclats de Seuil et le fait à la première ; rejouable après le répit, sans seconde récompense. Limites : les formes du gardien ne suivent pas le niveau du personnage (stats fixes, « difficile ») ; pas de modèle dédié (aucune dépense).

## Caravanes et attaques des bandits (sous-lot V2.41.1)

Plan de la grande carte, § 5 : **ce qui n'est pas vu est calculé, pas simulé**.

- **Place d'une caravane** (`CaravanSchedule.At`, fonction pure) : du temps du monde en millièmes de minute (`CaravanSchedule.MilliAt`, même découpage que `WorldClock.At`), de l'occurrence de son attaque (tirée comme tout événement du monde, `WorldEventSchedule.InWindow`, le premier jour de sa fenêtre) et de l'issue gardée au registre des événements (sauvegarde inchangée). Elle avance à vitesse constante le long de sa route (distances en `Fixed`, racine entière `IntMath.Sqrt`). Le jour d'une attaque, elle s'arrête à sa halte de son arrivée à la fin de l'attaque (état `Attacked`, aussi après la fin tant que l'issue n'est pas réglée) ; **pillée**, son épave reste à la halte (`Pillaged`) jusqu'à la fin des conséquences (`aftermathMinutes`, bornée à la fin du lendemain) ; **sauvée ou passée**, elle repart de la halte à la fin de l'attaque. Affichage seulement : ni la caravane ni ses gardes ne sont des combattants (écart au plan, voir les limites).
- **Attaque** : événement du monde de sorte `Caravan` (`WorldEventKind`, valeur 3, jamais lue d'un fichier de zone). Même mécanique qu'une attaque de lieu : annonce, bandits qui arrivent dans le secteur de la halte (ou au temps du monde, secteur fermé), réussite quand plus aucun bandit n'est debout et que le joueur en a blessé un, récompense entière la première fois, registre, réputation, contrecoups des marchands.
- **Issue sans le joueur** : quand le joueur est absent (attaque rattrapée au retour, ou, dans la même session, aucun bandit combattu ni blessé par lui, secteur de la halte ouvert ou fermé : réglée comme une absence `Missed`, revue Codex de la PR #240), un tirage fixe par occurrence (`CaravanSchedule.GuardsHold` : `Pcg32` de la clé de l'occurrence et de « caravan-guards: » + l'attaque) dit si les gardes tiennent seuls (`guardsPercent`) : la caravane **passe**, réglée sans issue (`EventOutcome.None`, annonce `Escaped`, texte « passee ») ; sinon elle est **pillée** (`Lost`, fait `lostFact`, contrecoup). **Joueur présent qui perd** (bandits encore debout à la fin de l'attaque) : la caravane est **pillée**, sans tirage (décision de Damien du 21 novembre 2026).
- **Prime** : à chaque caravane sauvée après la première, `reward.bounty` cuivre (si la bourse la tient ; sinon rien), annoncée comme une récompense.
- **Contrecoup** (marchands 0.22.0) : il part du **dernier pillage** (`lostDay` du registre, sauvegarde v30), pas de la dernière issue : pillée au jour J puis sauvée à J+1, les étals restent touchés jusqu'à la fin de J+2 (revue Codex de la PR #240) ; `caravane_pillee`, pendant 3 jours après une caravane pillée, les marchandises qu'apporte la caravane (épices et fruits du Sud, fil, cape de laine, braies de toile) tombent à 40 % du stock chez tous leurs marchands, à 125 % du prix.
- **Contenu** (caravanes 0.1.0 ; fréquence, gardes, récompense et prime, contrecoup : **décisions de Damien du 21 novembre 2026**, [plan](PLAN_GRANDE_CARTE.md)) : la **caravane d'Ambre**, chaque jour à partir du jour 1, part à 8 h du poste de péage (−1 600, −170), traverse le Bourg, le village, la mine, passe sous le fort et s'arrête aux lacets du col (1 600, 849,7), à 11,25 m par minute du monde (1,5 m/s), deux chariots, deux gardes. Attaque `attaque_caravane_d_ambre` : 35 % des jours, halte (1 310, 870) sur la route d'Ambre, sous le fort ; annonce 30 min, durée 90 min, conséquences 12 h ; niveau 18 au moins ; deux variantes (embuscade : trois bandits du fort et un archer ; archers : deux archers et deux bandits) ; gardes 50 % ; récompense 1 200 points d'expérience, 8 or, deux potions de soin, fait `fact.event.attaque_caravane_d_ambre.sauvee` ; prime 2 or ; fait d'échec `fact.event.attaque_caravane_d_ambre.pillee` (textes 0.45.0).
- **Quête de reprise au fort** (sous-lot V2.41.3, décision de Damien du 21 novembre 2026 ; caravanes en version 2, `recovery` ; sauvegarde v31) : un pillage laisse les coffres de marchandises au fort (annonce `RecoveryOpened`, texte « reprise_ouverte »). La quête est ouverte **du jour du pillage au soir du troisième jour** (`days` : 3 ; fermée à J+3). Le joueur reprend chaque coffre (`WorldSession.TakeCaravanChest`, `AdventureSession.TakeChest` ; touche d'action `Interact` (F, action tactile), après la faille et la cicatrice, avant portes et PNJ, indice « F : reprendre le coffre », revue Codex de la PR #243) à 3 m au plus, **quand aucun ennemi n'est debout à moins de 12 m** (`guardRadius`) : il faut d'abord battre les bandits du fort qui le gardent (refus `Guarded`). Refus atomiques : `Unknown`, `Closed` (pas de pillage, délai passé, tout repris), `Taken`, `NotHere` (tombé ou trop loin), `Guarded`, `Full`. Les coffres repris sont gardés au registre (`events[].recovered`, masque), remis à zéro à chaque nouveau pillage (la quête repart pour le dernier pillage, trois jours à partir de lui). **Chaque coffre repris enlève un jour au contrecoup** des marchands (`ShockActive` : `days − coffres repris` pour un contrecoup d'échec) ; **les trois repris, il est annulé** et la récompense est donnée : **à la première reprise complète, 400 points d'expérience (sous le plafond) et 2 or ; ensuite, 2 or seulement, sans expérience** (décision de Damien du 21 novembre 2026, anti-triche, comme la prime d'une caravane sauvée ; gardé par `events[].recoveredOnce`, sauvegarde v31) ; l'or si la bourse le tient, sinon rien ; annonce `Recovered` (« reprise », ou « reprise_sans_or » quand rien n'est payé) ; chaque coffre : `ChestRecovered` (« coffre »). Contenu (caravanes 0.2.0, textes 0.46.0) : trois coffres dans l'enceinte du fort, (1 180, 1 016), (1 206, 994), (1 240, 1 018), chacun à moins de 9 m d'un bandit du fort. **Décidé par Damien le 21 novembre 2026** (recommandations de la PR #243 validées) : récompense de 400 xp et 2 or à la première reprise complète, puis 2 or seuls (anti-triche, même jour) ; un jour de contrecoup en moins par coffre, annulé avec les trois ; un deuxième pillage fait repartir la quête à zéro ; le chef des bandits reste à son camp.
- **Affichage** (revue Codex de la PR #243) : `AdventureSession.FortChests` (`CaravanLooks.RecoveryChests`) donne les coffres encore à reprendre ; `CaravansView` (Unity) les pose au fort avec le modèle `coffres_marchandises` (formes simples sans lui) et retire l'instance d'un coffre repris ou d'une quête fermée.
- **Limites** : la caravane et ses gardes ne se battent pas (les bandits ne visent que le joueur) ; une seule caravane, dans un seul sens ; pas encore de journal de la quête de reprise ; le chef des bandits (à son camp, loin du fort) n'y joue pas de rôle ; pas de fait appris à la reprise.

## Architecture

```
rules.json ──► EdS.Data.Json (analyseur JSON strict maison, netstandard2.1 : outils .NET, Unity, serveur)
                    │ forme : syntaxe, types, champs inconnus/en double, nombres
                    ▼
               RulesDocument ──► RulesValidator (EdS.Data, commun)
                                    │ en-tête, champs obligatoires, références
                                    ▼
                               StatRules / DamageRules / ProgressionRules / CombatRules .Validate (domaine)
                                    │ seule validation de gameplay
                                    ▼
                               LoadedRules (règles + versions + empreinte)
```

- `EdS.Data` (netstandard2.1, aucune dépendance) : modèle `RulesDocument`, catalogue `RulesCatalog` (unique description du format), validateur commun, empreinte.
- `EdS.Data.Json` (netstandard2.1, C# 9, aucune dépendance depuis le sous-lot 9.1) : lecture de la forme, sans réflexion, sur un analyseur JSON strict maison (`EdS.Data.Json.Text`) qui remplace System.Text.Json : RFC 8259 sans extension (ni commentaire, ni virgule finale, ni NaN, ni marque d'ordre dans un texte ; un fichier lu par `JsonInput.ReadFile` est débarrassé de la sienne), profondeur bornée (`InputLimits.MaxJsonDepth`), nombre de valeurs borné pendant l'analyse (`InputLimits.MaxJsonValues`, voir les limites des lecteurs ci-dessous), arbre compact (aucun objet alloué par valeur, tableaux à la taille exacte), UTF-8 valide, texte brut des nombres conservé, propriétés et doublons dans l'ordre du texte, ligne de chaque nom de propriété. Il est comparé à System.Text.Json sur tous les fichiers livrés et figés, sur des valeurs aléatoires et sur des textes altérés (`Lot91JsonTextTests`) : même arbre, jamais plus laxiste ; il refuse en plus les paires de substitution UTF-16 incomplètes (`\ud83d` seul), que System.Text.Json admet à l'analyse. Les messages d'erreur de syntaxe (`InvalidJson`) sont en français ; codes, chemins et lignes inchangés. Unity et le futur serveur lisent donc les données exactement comme la CLI : même validation, mêmes empreintes.
- `EdS.Tools` (net10.0) : outils réservés à .NET, aujourd'hui les mesures des builds (`EdS.Tools.Measures`, sous-lot 8.6, rapport JSON écrit avec System.Text.Json).

## Empreinte

`sha256:…` calculée sur une écriture canonique (version du contrat canonique, version de schéma, puis chaque paramètre dans l'ordre du catalogue). Indépendante des espaces, de l'ordre des clés et de l'écriture des nombres (`2` = `2.0`) ; ignore `contentVersion`. Valeur actuelle de `data/v0/rules.json` :

```
sha256:0413744ac77641fff7ad7b45c86d46f2b2ee048e3ad48f3374236950e43866c9
```

**Contrat canonique 2 (correctif 7.3.1, A73-M02).** Une ligne par champ : `chemin=valeur` pour une valeur présente (barre oblique inverse, retour à la ligne et retour chariot échappés), `chemin?` pour un champ facultatif absent, et pour une liste `chemin.count=n` puis `chemin[i]=élément`. Aucune valeur textuelle ne sert plus de sentinelle : au contrat 1 (lots 1 à 7.3), un champ absent s'écrivait `none` (ou une chaîne vide dans les classes) et une liste était jointe par des virgules, si bien qu'un `filter.status` ou un `grantsOnExpiry` absent avait la même empreinte que la valeur `none`, identifiant d'altération valide (deux collisions démontrées par l'audit). Le texte haché commence par `eds-rules` ou `eds-class` puis `canonical=2`. Écrit par `CanonicalWriter` (`EdS.Data`) pour les règles, les altérations, les déclencheurs et les classes. **Compatibilité** : toutes les empreintes changent ; un journal antérieur (moteur 0.9.0, contrat 1) est refusé au rejeu avant toute simulation (moteur et empreintes différents), sans migration ; les quatre journaux de référence 0.9.0, figés dans `tests/EdS.Data.Tests/Fixtures/logs-0.9.0`, ne diffèrent des actuels que par `engineVersion` et les empreintes de l'en-tête.

**Politique pré-alpha : aucune migration garantie.** Un fichier d'une version antérieure est refusé explicitement, par un seul message sur `$.schemaVersion` (`UnsupportedSchemaVersion`, « structure incompatible, refusée ; aucune migration n'est garantie »), sans analyse de son contenu : pas de cascade de champs manquants. Il se met à jour à la main en suivant ce document. Une version future est refusée de la même façon. Les migrateurs automatiques n'arriveront qu'avec un format stabilisé.

Contrat des chaînes (correctif 6.1) : `contentVersion` suit SemVer 2.0 strictement (chiffres ASCII, pas de zéro initial, y compris dans les identifiants numériques de pré-version, toute la chaîne : un saut de ligne final est refusé). Identifiants stables et noms de combattants : minuscules ASCII, chiffres et `_`, correspondance de toute la chaîne.

## Erreurs

Chaque erreur donne un chemin JSON, un code stable et, quand c'est possible, la ligne :

```
$.data.stats.base.maxHealt (ligne …) : champ inconnu ; champs possibles : physicalPower, … [UnknownField]
$.data.damage.defenseConstants.feu (ligne …) : type de dégâts inconnu « feu » ; valeurs possibles : physique, magique. [UnknownReference]
$.data.stats.critical.maxChanceBasisPoints : la chance critique maximale ne peut pas dépasser 10 000 points de base (100 %). [InvalidValue]
```

Bornes techniques des règles (correctif 6.1.1) : `damage.defenseConstants.*` dans ]0, 10⁹], `combat.globalCooldownMs` et `combat.endurance.regenDelayMs` dans [0, 86 400 000] ms, comme les autres durées. Une valeur **calculée** hors des limites numériques du moteur (défense effective d'un personnage, pire impact, cumul) est refusée à la validation du scénario avec le code `OutOfRange`, sur le chemin du combattant (`$.data.combatants[0]`). Voir [MOTEUR.md](MOTEUR.md#limites).

Limites de volume (sous-lot 7.1) : les cinq champs de `combat.limits` ajoutés en schéma 3 sont bornés par des plafonds techniques (`maxCombatants` [2, 256], `maxCommands` [0, 10⁶], `maxCommandsPerActorPerTick` [1, 64], `maxPendingEvents` [1, 10⁷], `maxWorkPerTick` [1, 10⁷]) et `maxEventsPerTick` ne peut pas dépasser `maxWorkPerTick`. Un scénario qui dépasse une limite configurée est refusé avec le code `LimitExceeded` : sur le tableau (`$.data.combatants`, `$.data.commands`, une seule erreur, sans analyser les éléments), sur `$.data.commands[i].atMs` pour la première commande en excès d'un acteur à un tick, ou sur `$.data.commands` si les événements initiaux dépassent la capacité de la file.

Limites des lecteurs (sous-lot 7.1, constantes techniques) : fichier de données ou texte JSON au plus 16 Mio (`FileTooLarge`, vérifié avant lecture ou avant encodage), profondeur JSON au plus 32 (`InvalidJson`), document JSON d'au plus 1 048 576 valeurs (sous-lot 9.1, revue de la PR #12 : objets, tableaux, textes, nombres et littéraux, racine comprise ; `LimitExceeded` sur `$` avec la ligne, compté avant la création de chaque valeur : un texte valide de 16 Mio de « 0, » est refusé après 2 Mio lus, 32 Mio alloués au lieu de 700, alors que les fichiers livrés en ont moins de 1 000 et qu'un scénario de 20 000 commandes en a environ 120 000), journal rejoué au plus 256 Mio. Un rapport conserve au plus 200 erreurs ; les suivantes sont comptées et résumées par une dernière ligne « … et N autres erreurs ». Détail : [LIMITES_LOT_7.md](LIMITES_LOT_7.md#limites-des-lecteurs-en-place-sous-lot-71).

Codes : `FileUnreadable`, `DuplicateId`, `InvalidJson`, `WrongType`, `MissingField`, `UnknownField`, `DuplicateField`, `InvalidNumber`, `OutOfRange`, `UnknownReference`, `UnsupportedSchemaVersion`, `InvalidContentVersion`, `WrongKind`, `InvalidValue`, `LimitExceeded`, `FileTooLarge` (sous-lot 7.1). Toutes les erreurs sont rapportées en une passe, dans la limite de 200.

## Commande

```bash
dotnet run --project src/EdS.Cli -- validate                  # data/v0/rules.json
dotnet run --project src/EdS.Cli -- validate chemin/rules.json
dotnet run --project src/EdS.Cli -- validate data/v0/classes/bastion.json [--rules chemin/rules.json]
dotnet run --project src/EdS.Cli -- validate data/v0/builds/bastion.json   # sous-lot 8.5
dotnet run --project src/EdS.Cli -- carte cases [--ids]               # sous-lot V2.25.3 : cases occupées et leur contenu
dotnet run --project src/EdS.Cli -- carte densite [--vides]           # points d'intérêt par case (une ligne par rangée, du nord au sud)
dotnet run --project src/EdS.Cli -- carte image --out carte.png [--pixels-par-case 16] [--cadre c13_r11:c16_r14]
```

`eds carte` lit une zone à région (défaut : `data/v0/world/zones/vallons.json`, options `--zone`, `--data`, `--scenarios`) et n'écrit rien dans les données. `densite` : « . » case sans rien, « o » décor seulement, 1 à 9 points d'intérêt, « + » au-delà ; `--vides` liste les cases sans point d'intérêt. `image` : PNG RVB, cases teintées selon leur densité, lignes des cases (gris clair) et des secteurs (gris foncé), aire praticable (bleu), obstacles (gris, bas en bleu clair), lieux (orange), routes (brun), points sûrs (bleu), portes (rouge), populations (vert) ; mêmes données, mêmes octets. Code 1 sur une option invalide, une zone refusée ou sans région.

Le champ `kind` choisit le validateur. Un fichier de classe est vérifié avec la progression du `rules.json` indiqué (défaut : `data/v0/rules.json`) ; un fichier de builds, avec les règles et les classes de `data/v0` (sans ses builds), et chaque build est résumé (points par arbre, majeur, emplacements).

## Scénarios et jeu de données (lots 5 et 6)

`GameDataLoader.Load("data/v0")` charge `rules.json`, tous les `classes/*.json` et, depuis le sous-lot 8.5, tous les `builds/*.json` en un `GameData` (règles, classes, builds de référence, identité : versions et empreintes des règles et des classes). `ScenarioJsonReader` (forme) → `ScenarioDocument` → `ScenarioValidator` (en-tête, références de classe, build validé par `BuildValidator`, puis `CombatSetup.Validate`) → `CombatSetup`. L'identité retenue pour le journal ne couvre que les règles et les classes utilisées par le scénario. Depuis le lot 6, un scénario peut contenir un assaillant (`type: "assailant"`) et des commandes défensives (`action`). Format, exemples et rejeu : [MOTEUR.md](MOTEUR.md).

**Combat positionné (schéma 5, sous-lot 11.4a).** Un scénario peut porter un bloc `space` ; alors chaque combattant a une place de départ, et seulement dans ce cas :

```json
"space": {
  "bounds": { "min": [-10, -6], "max": [10, 6] },
  "obstacles": [ { "id": "rocher", "points": [[-4.5, -0.2], [-3.5, -0.2], [-3.5, 2], [-4.5, 2]] } ]
},
"combatants": [ { "id": "bastion", "…": "…", "position": [-6, 0.5], "facing": [1, 0], "radius": 0.5 },
                { "id": "loup", "type": "assailant", "…": "…", "position": [8, 0.4], "radius": 0.6, "speed": 6 } ],
"commands": [ { "atMs": 0, "actor": "bastion", "action": "move", "direction": [1, 0] },
              { "atMs": 2200, "actor": "bastion", "action": "stop" } ]
```

Un point s'écrit `[x, z]` en mètres (x vers l'est, z vers le nord), dans ±1000 m. `obstacles` est facultatif (au plus 64 polygones strictement convexes de 3 à 16 sommets, dans un sens ou dans l'autre, identifiants uniques) ; `position` et `radius` (0,1 à 5 m) sont obligatoires, `facing` facultatif ([0, 1] par défaut, composantes dans [−1, 1]), `speed` (0,1 à 20 m/s) réservé aux assaillants. L'emprise de départ tient dans l'aire et ne chevauche ni un obstacle ni un combattant qui lui est solide. `move` exige `direction` (composantes dans [−1, 1], non toutes deux nulles) ; `stop` et les autres actions n'en ont pas ; un déplacement sans `space` est refusé. Chaque erreur a son chemin (`$.data.combatants[1].position`, `$.data.space.obstacles[0].points`, `$.data.commands[0].direction`…).

**Attaques annoncées (schéma 6, sous-lot 11.4c).** Dans un combat positionné, une attaque d'assaillant (`targeting: enemy`) peut avoir une forme ; tous les champs sont facultatifs et seuls ceux de sa forme sont admis ([MOTEUR.md](MOTEUR.md#attaques-annoncées-et-garde-de-face-sous-lot-114c)) :

```json
{ "id": "ecrasement", "rawDamage": 120, "damageType": "physique", "targeting": "enemy", "unblockable": false, "applies": [],
  "shape": "circle", "telegraphMs": 900, "radius": 2 },
{ "id": "souffle", "…": "…", "shape": "cone", "telegraphMs": 1100, "range": 8, "angle": 90, "guardable": true },
{ "id": "coup", "…": "…", "shape": "target", "range": 2.5 }
```

| Champ | Formes | Sens et bornes |
|---|---|---|
| `shape` | — | `target`, `cone`, `circle`, `line`, `persistent` ; absente : attaque historique (la cible ou tous les ennemis, sans géométrie) |
| `telegraphMs` | toutes | durée de l'annonce (ms, multiple du tick, 0 par défaut) ; une zone doit laisser `combat.telegraph.minReactionMs` + le temps d'en sortir au pas de base |
| `range` | `target` (facultatif), `cone`, `line` | portée (bords des emprises) ou longueur, 0,1 à 100 m |
| `radius` | `circle`, `persistent` | rayon, 0,1 à 100 m |
| `angle` | `cone` | ouverture, 1° à 180° |
| `width` | `line` | largeur, 0,1 à 100 m |
| `center` | `circle`, `persistent` | `target` (défaut) ou `self` |
| `persistentMs`, `tickMs` | `persistent` | durée de la zone et cadence de ses impacts (ms, multiples du tick, `tickMs` ≤ `persistentMs`) |
| `guardable`, `parryable` | toutes, attaques historiques comprises | défenses admises ; défauts et interdits : voir MOTEUR.md (jamais de parade contre une zone, jamais de garde contre une zone persistante ni contre une attaque imparable) |

Action `select` (combat positionné) : `{ "atMs": 0, "actor": "bastion", "action": "select", "target": "ogre" }`, sans `target` pour effacer la sélection ; elle ne prend pas de compétence. Le protocole du lot 10 ne la transmet pas.

**Arrivées et départs (schéma 7, sous-lot 11.4d).** Un combattant peut porter `arrivalMs` (entier, multiple du tick, dans [0, durée[) : il arrive en cours de combat, au début de ce tick ; absent : présent dès le départ. Sa place (combat positionné) est contrôlée comme celle des autres pour l'aire et le décor, mais pas contre les autres combattants : c'est le moteur qui refuse l'arrivée si une emprise solide l'occupe à ce moment-là. Action `leave` (avec ou sans espace) : `{ "atMs": 5000, "actor": "renfort", "action": "leave" }`, sans compétence ni cible, effective en fin de tick ([MOTEUR.md](MOTEUR.md#arrivées-départs-et-instantané-détat-sous-lot-114d)). Le protocole du lot 10 ne la transmet pas. Scénario livré : `scenarios/espace_renfort.json`.

**Comportements et charge (schéma 8, sous-lot 11.5).** Un assaillant d'un combat positionné peut porter `behavior` : `{ "maxRange": 0.5, "aggroRange": 8, "encircle": true }` (loup), `{ "maxRange": 9, "minRange": 6, "aggroRange": 14 }` (archer). `maxRange` obligatoire, `minRange` (0 par défaut, au plus `maxRange`), distances dans [0, 100] m entre les bords ; `aggroRange` dans ]0, 100] m, absente : engagé d'emblée ; `encircle` faux par défaut. Avec un comportement, `target` devient facultative, omise ou nulle (l'ennemi prend le plus proche) et le scénario ne lui donne ni `move` ni `stop`. Une bande peut être une charge : `"shape": "line", …, "charge": true` (seulement une bande). Fonctionnement : [MOTEUR.md](MOTEUR.md#comportements-des-ennemis-sous-lot-115). Scénario livré : `scenarios/espace_meute.json`.

**Réglages après l'essai (schéma 9, sous-lot 11.9).** Un obstacle peut être bas : `{ "id": "riviere_sud", "points": [...], "low": true }` (arrête la marche, pas la vue). Une bande peut repousser ce qu'elle touche : `"shape": "line", …, "push": 2` (mètres, dans [0,1 ; 100], seulement une bande). Une attaque à forme peut laisser l'ennemi se placer pendant son annonce : `"holdPosition": false` (vrai par défaut ; refusé sur une attaque sans forme). Un comportement peut être solitaire : `"behavior": { …, "pack": false }` (vrai par défaut : la meute l'entraîne). Une marche peut se faire à reculons : `{ "atMs": 0, "actor": "bastion", "action": "move", "direction": [-1, 0], "backward": true }` (l'orientation ne suit pas la marche ; refusé sur une autre action). Fonctionnement : [MOTEUR.md](MOTEUR.md#réglages-après-lessai-sous-lot-119). Scénarios des Vallons (`vallons_demo`, `coop/vallons_duo`) : rivière basse, sanglier qui repousse de 2 m, sanglier et archer hors meute, pluie de flèches sans arrêt.

**Zone (schéma 10, sous-lot 12.1).** `"zone": true` dans `data` : le scénario décrit une zone du monde (combat positionné : `space` obligatoire ; une seule équipe ou aucun combattant admis ; durée jusqu'à 86 400 000 ms, 24 h). Fonctionnement : [MOTEUR.md](MOTEUR.md#mode-zone-sous-lot-121). Scénario livré : `scenarios/zones/vallons.json` (les Vallons sans personnage, une heure par session).

Dépendances (lot 6) : la description d'un combat (`CombatSetup`, combattants, commandes, identité des données) est passée d'`EdS.Simulation` à `EdS.Domain` (espace `EdS.Domain.Combat`). `EdS.Data` ne dépend donc plus que du domaine ; seuls `EdS.Data.Json` (rejeu) et les outils (`EdS.Tools`, `EdS.Cli`) référencent le moteur pour simuler et rejouer.

```
EdS.Domain ◄── EdS.Simulation ◄── EdS.Data.Json ──► EdS.Data ──► EdS.Domain
                     ▲                  ▲
                     └──── EdS.Tools ───┘      (netstandard2.1 à gauche ; EdS.Tools et EdS.Cli en net10.0)
                              ▲
                           EdS.Cli
```
